## 分类与最小修正

只有从页面观察出发、三份干净页面稳定复现的必要问题进入生产修改。

### A / P2：媒体未就绪时播放等待没有终态

用户输入一个格式合法但不存在的 RTSP 地址，开始取流提示成功；随后点击播放，认为等待会成功或失败。实际一分钟仍显示正在连接，源行操作受 pending 禁用，只能先关闭播放器再猜测补救动作。

三次新浏览器/新源复查均为 RED：30.05、35.05、35.05秒仍连接；分别观察30、35、35个 POST，全部即时409。不是单个 WHEP POST 悬挂。真实正确 URL 能播放，排除了整个 PeerConnection 或夹具失效。

定位后只给既有 RTSP 409 就绪重试加一个局部30秒预算：持续未就绪达到预算后，下一次409抛出现有 `whep_create_409`，沿用清理与「播放失败 / 媒体尚未就绪，请稍后重新播放」。独立原始探针 GREEN 为30.25秒、31个409；没有再无限请求。错误地址的上游仍由用户停止并编辑，未加入自动恢复。

这是重试总等待预算，**不是抢占单个 fetch 的硬30秒 timeout**。既有 Retry-After 最多5秒，截止判断在409返回后发生；合法迟到201仍走原资源清理。没有新增 controller、timer、长期字段、错误码或 retry loop。GB 一次 fresh-ticket 重试、transport failed 与 source ended 的区别保持。

GB代理已有 media client timeout 与读/写 deadline；RTSP C++ handler 同步查流、解析、创建并返回，不等待 ICE/DTLS/首帧，HTTP I/O 使用既有 Beast expiry。没有证据要求修改单次 POST timeout 或 C++。先前单请求审计结论仍成立，本轮的新证据针对409循环。

### D / P2：新设备离线后缺少下一步

用户保存设备后进入详情，认为平台可能会主动接入设备。原提示只有「设备恢复在线后…」，新安装设备并没有“恢复”这一前情；点击刷新也只是仍离线。

三份干净页面均复现缺少检查方向。只替换一行提示为「请检查设备网络与平台接入配置，上线后可查看通道与播放」。设备端具体配置仍是产品边界，没有增加向导、平台配置接口或自动探测。

### C/D / P2：运行中的编辑入口消失

用户正在看后门画面，想改更准确的名称；此前保存后可见的铅笔消失，只能试着停止取流才重新找到入口。三次干净页面均为运行时无编辑、停止后恢复。

保留同一编辑图标，运行时禁用，title/accessible label为「停止取流后可编辑」。停止后恢复原「编辑」。使用已有 source.session 和 pending，不开放运行中编辑，不加说明区、helper或状态。

### C / P2：窄窗播放时视频盖住源操作

修改后正常使用中，用户在600px窗口看完RTSP，想直接停止上游。实际视频与源列表重叠，停止按钮被视频截获，必须先关闭播放器才能操作源。

三份干净页面普通点击均失败并明确记录 preview-video 拦截。另在独立浏览器中仅将app.js响应替换为BASE_HEAD版本，保留真实后端、媒体网络和原生PC，停止按钮中心命中VIDEO，证明不是新增编辑图标造成。

窄屏通用规则将播放器放第2行，RTSP源 workspace 也在第2行。只在已有RTSP播放器选择器补 `grid-row: 1`，不改其他布局规则。修复后播放器底部580.5、源列表顶部604.5；通过正常滚动和普通点击停止，未使用 force。没有改冻结的300 CSS px最小宽度边界。

## 十九项产品问题回答

| 问题 | 本轮结论 |
| --- | --- |
| 1. 首次从哪里开始 | 添加设备是主要入口；有RTSP URL时另一个入口明确。接入配置不能仅靠本页完成。 |
| 2. 添加后离线 | 已创建与在线可区分；原提示缺行动方向，已最小修正。 |
| 3. 上线/Catalog | 不刷新自动出现在线/通道；捕获独立同步提示；稳定空目录明确检查配置。不能由400ms采样保证所有网络都无闪烁。 |
| 4. 三种主要动作 | 十次结果反馈后形成清晰范围；关闭保留上游，停止结束媒体。 |
| 5. GB/RTSP模型 | 观看与上游范围一致；RTSP显式开始后播放，GB播放会按需开始，是真实策略差异。 |
| 6. 多设备查找/返回 | 短列表直接选；大列表有滚动成本；位置、选择和焦点保留。 |
| 7. offline/re-online | 离线保留名称和结束原因，通道替换为空态；重新上线无需刷新，主动重播。 |
| 8. 错误后下一步 | 管理连接、停止失败、播放连接失败都有行动提示；未就绪原来没终态，现可停止并改地址/重播。 |
| 9. 服务恢复 | media恢复后原停止入口补偿、再播放成功；signaling恢复后更新时间继续、设备重新接入，RTSP从开始入口恢复，不reload。 |
| 10. 犹豫 | 编码误当IP、添加后等上线、消失的编辑、两列状态、停止失败仍可点、RTSP连接持续。后三种状态通过实际结果区分，必要问题已修。 |
| 11. 未使用信息 | 首轮未使用认证清空、设备删除、长编码排查；它们有低频管理价值，不机械删除。更新时间在故障时真正有用。 |
| 12. 多一步 | RTSP重开先开始再播放；改源前必须停止。保留策略，只明确编辑前置条件。 |
| 13. 技术正确但不自然 | 禁运行编辑却隐藏入口；接受拉流请求却让播放无限连接。已修可见反馈。 |
| 14. 需内部知识 | 旧界面无法解释编辑入口消失和无限等待；已给出入口/终态。设备接入细节仍需要设备资料，不假装本页涵盖。 |
| 15. 误操作风险 | 删除确认默认取消且目标明确；未观察误删。停上游与关闭画面可从行状态辨认。 |
| 16. 产品边界 | 外部接入配置、厂商/多通道、认证、部署规模搜索需求、WAN与浏览器泛化。 |
| 17. 新P0/P1/P2 | 无新P0/P1；四项必要P2，均稳定复现后最小修正。 |
| 18. 生产修改 | JS四行就绪截止、离线提示、保留禁用编辑、CSS一条行定位；不改API/Go/C++。 |
| 19. 新状态 | 无新长期字段。只有一次postOffer调用内的局部deadline，无新播放器状态机。 |
