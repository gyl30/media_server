# 阶段 3B：单协议性能对比矩阵

运行：`20261012T043240Z-76355e4` · TEST `<TEST_HOST>` · 命名空间 `msperf-20261012T043240Z-76355e4`
被测：`media_server` HEAD `76355e435a766ed6d6c58be5dc315d14256b4e65`，SHA256 `e8f8e298…`
工具：`perf_run`（`--server-cpus 0-7 --client-cpus 8-15 --client-dir build`）、真实 Go signaling、`perf_publish`（RTMP fixture）
矩阵：8 个输出协议 × {1, 10, 50, 100} viewer × 3 次重复 = **96 个正式用例 + 8 个能力探测 + 3 个 A3 校验，全部 PASS，0 失败**
原始数据：TEST `phase3-protocols/`（每用例 `result.json` + 客户端产物）、`extract.jsonl`（逐用例指标）、`aggregate.json` / `aggregate.csv`（按协议聚合）

## 方法

- 单一 fixture：1280×720@30fps H.264（1.53 Mbps）+ AAC（46.9 pkt/s）+ Opus（50 pkt/s），由 `perf_publish` 以 RTMP 注入，所有协议共用同一 source 形态。
- 每用例独立 DUT 进程与独立 source，`--warmup 10 --duration 30`，指标只取稳定窗口。
- 服务端指标：`/proc/<pid>` 1 Hz 采样（CPU、PSS/RSS、FD、线程、per-thread CPU、上下文切换、`task/*/io`、进程 PSI）+ 命名空间内 `ss`/`netstat`/`sockstat` 快照。
- 客户端指标：每个客户端进程独立 CPU/PSS/FD/per-thread 采样，用于证明客户端不是瓶颈。
- 媒体健康：客户端上报的覆盖率、就绪/推进/失败 viewer 数、消息与包计数、字节数、首包延迟分位数、`unprotect_failures`。
- 协议参数遵循默认：RTSP 默认 interleaved、GB28181 默认 PS、WHEP 默认转码路径、HLS 默认分段配置。

## 结论

1. **成本排序（每 viewer）**：HLS 0.41 ≪ RTMP 1.85 < GB TCP 1.92–1.93 < FLV 2.32 < RTSP 2.43 < GB UDP 2.66 ≪ WHEP 4.23 mCPU。
2. **HLS 明显最省**（每 viewer 成本约为其他协议的 1/5，100 viewer 仅 0.048 核）：分段文件可被多个 viewer 复用，服务端只做 playlist + 分片读取；代价是端到端延迟与首片等待，不在本阶段度量范围。
3. **WHEP 明显最贵**：既有最高的每 viewer 成本（4.23 mCPU，约为 FLV 的 1.8 倍），又有最高的固定成本（拟合截距 0.084 核，1 viewer 实测 0.063 核）。同时它的线程上下文切换是其他协议的 1.7 倍（19 000 vs 11 400 / 30 s），且成本集中在单个工作线程（100 viewer 时该线程 0.105 核）。这与 AAC→Opus 转码 + SRTP 逐 viewer 加密的路径一致，但**固定成本究竟属于 per-source 还是 per-viewer，本阶段无法区分**（1 source × N viewer 的矩阵天然无法分离两者），需在阶段 4 用多 source 固定 viewer 数验证。
4. **GB28181 三种传输的对比**：TCP active ≈ TCP passive（1.92 vs 1.93 mCPU，差异在噪声内），**UDP 比 TCP 贵约 38%**（2.66 vs 1.92 mCPU），且每 viewer 多 1 个 FD、PSS 增长却最小。原因是 UDP 路径每 viewer 独立 socket（额外 recv 缓冲与 syscall），TCP 路径共享监听与流式解析。这是本阶段唯一明确的传输层差异，值得在阶段 6 用 perf 采样确认 syscall 占比。
5. **FLV 与 RTMP 的差异**（2.32 vs 1.85 mCPU，+25%）来自 HTTP chunked 封装与每 viewer 的 HTTP 响应路径；两者媒体内容完全相同。
6. **RTSP 与 FLV 基本同价**（2.43 vs 2.32），RTSP 的 RTP 打包（176 包/s/viewer）没有表现出显著额外成本。
7. **100 viewer 内没有任何饱和迹象**：所有协议 R² ≥ 0.98、线程未饱和、PSI 全程 0.00、无队列积压。按线性外推，8 核预算（例如 4 核可用）下 WHEP 约 940 viewer、FLV 约 1 700 viewer、HLS 约 9 700 viewer 才会耗尽 CPU；**这只是算术外推，不是容量边界**，真实边界由阶段 5 给出。

## 限制

- 单一 fixture（720p30 / 1.53 Mbps / 30 fps）。每 viewer 成本与码率、帧率、分片大小强相关，不能直接换算到其他媒体形态。
- 1 source × N viewer：无法分离 per-source 与 per-viewer 成本（WHEP 固定成本归属未知），阶段 4 处理。
- 未测端到端播放延迟、卡顿与音视频同步；本阶段只证明"媒体完整且速率正确"。
- 未测断流重连、generation 替换与 churn；已在阶段 2.3 单独验证正确性，不含性能边界。
- 阶段 1 记录的 off-CPU 采样环境缺陷仍然存在，本阶段未做 off-CPU 归因；上述"原因"均为待验证假设，不是已证实的因果。
