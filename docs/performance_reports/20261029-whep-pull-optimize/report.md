# WHEP Pull 极限性能优化

起点 `cb03380`（上一轮审查基线），8 个物理核。本轮保留并本地提交了 3 个提交（一个工具、一个生产改动、一个文档），未推送。另外做了两项隔离实验：FFmpeg AAC 编码器补丁和 libfdk-aac。实验不进入正式实现，等待用户决定。

## 1. 结论

**在固定 8 核下，WHEP Pull 提高了多少路？**

| 版本 | 状态 | 最大持续容量 | 正常稳定容量（留余量） | 每路成本 |
| --- | --- | --- | --- | --- |
| 原版 `cb03380`，生产式混合放置 | 原状 | 125 路只有 1/3 通过，150 路 0/6 | 约 100 路（见上一轮报告） | 103–105 Mcyc/s |
| 原版，理想的顺序建流（全均匀） | 原状 | 160 路（上一轮 170 路 2/2 失败） | 160 路（最忙 CPU 0.91） | 104.8 |
| **会话最少放置 `a636699`（已提交）** | 正式 | **168 路**（顺序 168 4/4、混合 165/168 各 1/1，最忙 CPU 0.95–0.96）；176 路失败 | **160 路**（顺序 1/1、混合 2/2，最忙 0.91–0.92） | 104.5 |
| 放置 + FFmpeg `aaccoder` cbrtf 查表补丁 | 隔离实验，输出逐字节相同 | **184 路**（顺序、混合各 1/1，最忙 0.98）；192 路失败 | 176 路（顺序、混合各 1/1，最忙 0.93） | 97.5–98.0 |
| 放置 + libfdk-aac（afterburner） | 隔离实验，需许可决定 | **300 路**（顺序、混合各 1 次，最忙 0.94–0.95）；320 路失败 | 280 路（混合，最忙 0.88） | 58 |

- 生产流量下（建流请求与其他连接混在一起），已提交的改动把稳定容量从约 100 路提到 160 路，最大持续从不足 125 路提到约 168 路。
- 理想均匀建流时，原版本来就能到 160 路，放置改动不降低这一能力（seq160 原版、新版都通过，每路周期相同）。新版的价值在于：真实混合流量下也能达到这一上限。
- 在此基础上，继续提升只能降低单路成本。单路成本 81% 是 FFmpeg 原生 AAC 编码。
  - 不改音质的前提下，可做的有两条：
    - FFmpeg 补丁：每路 -6.4%，最大持续到 184 路；
    - 换 fdk 编码器：每路 -44%，最大持续到 300 路。
  - 两条都改动外部依赖（第 9 节），本轮只做隔离验证，没有并入正式实现。

**主要收益来自哪里？**

1. **均衡（已提交）**。单 worker 的上限约 21 路（同步 AAC 编码打满一个核），总容量只取决于“最忙 worker 有多少路”。
   - 原放置跟随 HTTP 连接，连接按全局轮转，混合流量下 150 路分布为 25/22/22/18/18/17/14/14，最忙 worker 先饱和。
   - 现在选会话最少的 worker，150 路为 19×6 + 18×2，160 路为 20×8。
2. **AAC 编码成本（实验）**。cbrtf 查表补丁消除了 ESC 码本中每个系数的 `cbrtf` 调用；fdk 编码器每秒周期只有 FFmpeg twoloop 的约 1/3，客观音质指标更好。

**还能不能继续增加？代价是什么？**

- 不改依赖：已到上限。
  - 正式版每路 104.5 Mcyc/s，8 核满频约 18.4 Gcyc/s，理论值 176 路。实测 168 路时最忙 CPU 已到 0.96，176 路丢包失败。
  - 非 AAC 部分合计不到 20%（Opus 解码 6.4%、syscall 3.4%、SRTP/RTP/H.264 2.2%、拷贝 2.3%），即使全部消除也只能多约 40 路，而且每项都是 1–3% 的零碎工作。
  - 编译参数（`-march=x86-64-v3`）只省 2%；FFmpeg twoloop 其余热点是平摊的浮点运算。均不值得做。
- 打 FFmpeg 补丁：+16 路。代价是维护一个本地 FFmpeg 补丁（约 12 行，输出不变），或推到上游。
- 换 libfdk-aac：+132 路。代价：
  - 许可。fdk 与当前 GPLv3 的 FFmpeg 构建不兼容。可行做法是为 media_server 单独构建精简 LGPL FFmpeg（media_server 只用 Opus/AAC/swresample/swscale），FFmpeg configure 已确认 LGPL + fdk 无需 nonfree。FDK 自身许可与 AAC 专利需要法务确认。
  - 部署多一个依赖。
  - 音画偏差多约 26 ms（-51 → -77 ms，恒定）。

## 3. 方法

- **容量**：用 `perf_run` 在 netns 中逐级加压，边界附近重复测量，并同时覆盖：
  - 顺序建流（全均匀，`seqN`）；
  - 混合建流（`--pull-interleave-seed`，每次建流前插入 0–7 个随机控制请求，`mixN-sS`）。
- **判定**：沿用 perf_run 的 HEALTHY 判定，即全部观看者推进、无媒体停顿或运行时失败、服务端无 UDP 丢包、控制探测无错误。
  - 不放宽判定条件。
  - 判为 INCONCLUSIVE/CLIENT_RESOURCE 的轮次不计入容量。
  - 带 bpftrace 的诊断轮（`d-x-*`）只用于观察 worker 分布，不作为容量结论。
- **A/B**：同一批次内交替运行 A/L（混合 150 ×3 种子、顺序 160）和 P/L（顺序 168 ×3 对）。比较用周期数，不用 CPU 时间（原因：schedutil）。
- **测试台限制与处理**：
  - 观看端：默认 256 路共用一个观看进程。
  - 上游 egress：fdk 版 250 路以上时，上游 media_server 有 4 个线程打满。原因是 WHEP egress 按连接轮转，测试的连接序列有固定周期，见第 10 节。
  - 处理：新增 `--upstream-sources 64`，让多路拉流共享 64 个上游源及其 egress 转码器。
  - 服务端每路仍是独立的 WHEP 会话、SRTP 和转码。对照：正式版 168 路下，共享与不共享的每路周期分别为 104.1 与 104.5 Mcyc/s。
- **工具**：
  - `tools/aacbench/`：`aacbench` 直接驱动 FFmpeg/libfdk；`msbench` 链接真实 `audio_transcoder`；`build.sh`、`run.sh`。
  - `tools/quality/nmr.py`：简化的 PEAQ 式 NMR。
  - `tools/optsum.py`、`tools/wqsum.py`：结果汇总。
  - `tools/test-host/*.sh`：全部测试机作业。
  - `tools/sync.sh`：拉取原始数据到 `raw/`。

## 4. 各轮 profiling 发现

### R1 服务端转码比离线贵 1.55 倍的原因

上一轮测得服务端每路转码约 90 Mcyc/s，而离线 aacbench 只有 58。结论：差异来自输入信号，不是实现开销。证据：

- `msbench` 链接真实 `media_server::audio_transcoder`，配置与 `whip_media_receiver` 相同。
  - 输入 float→libopus 的语料：19.9 ms/音频秒，与 aacbench 一致；20 路交错不变。
  - 输入走真实上游链（AAC → media_server Opus egress → AAC）：32.2 ms/s。
  - 输入 s16→libopus 语料（与上游 egress 一致）：32.3 ms/s ≈ 90 Mcyc/s，复现了服务端实测。
- 上游 egress 编码 s16 样本，量化噪声使 twoloop 的量化搜索明显变重。`audio_transcoder` 本身（swr、FIFO、ADTS）的开销可以忽略。
- 推论：真实场景的单路成本取决于源音频；本报告的容量都基于 perf 夹具这一较重的内容。avsync 夹具每路只有 50 Mcyc/s。

### R2 Worker 分布（已提交的放置改动）

bpftrace 诊断（`raw/prof/x-*`，`wpsum.py`），按 worker 列出会话数（括号内为该 worker 的 CPU 繁忙度）：

| 轮次 | 每 worker 会话数（繁忙度） | 结果 |
| --- | --- | --- |
| 原版 mix150-s11 | 25(0.995)、22(0.996)、22(0.993)、18、18、17、14、14 | 前 3 个 worker 饱和丢包，FAIL |
| 新版 mix150-s11 | 19×6(0.90)、18×2(0.85) | PASS |
| 新版 mix160-s11 | 20×8(0.95) | PASS |
| 新版 seq170 | 22×2(0.997)、21×6(0.99) | 22 路的 worker 丢包，FAIL |

- 每路约 2.2 Gcyc ÷ 21 ≈ 105 Mcyc/s，与总量一致。
- 单 worker 承载上限：21 路（繁忙度 0.96）。
- 换算到 8 核：顺序与混合下最大持续都是约 168 路。

| 素材 | twoloop | fast | fdk ab=1 | fdk ab=0 |
| --- | --- | --- | --- | --- |
| perf 夹具 | -21.8 (0.1) | -37.9 (0) | -27.9 (0) | -25.5 (0) |

- **fast**：6 首歌中 5 首 NMR 更差，扰动帧普遍接近 100%。夹具上看似更好，是因为夹具内容过于简单。按“不降低音质”的约束拒绝。
- **fdk**：全部素材 NMR 比现状低 3.5–5 dB，扰动帧大幅减少。
- **局限**：歌曲源本身是 MP3；NMR 是简化模型，只适合同一参考下的相对比较，不是 ODG 绝对分。
- **兼容性**：fdk 输出 AAC-LC 48 kHz 双声道，ASC 与 ADTS 合法（`parse_aac_asc` 校验通过）。RTMP/FLV/RTSP/HLS 四种输出都能正常解码（见第 8 节）。

### R4 FFmpeg cbrtf 查表（隔离实验）

- 上一轮服务端 profile 中 `cbrtf` 占 6.56%。来源是 `libavcodec/aaccoder.c:140`：ESC 码本对每个系数计算 `c*cbrtf(c)`，源码中本来就带有 `//FIXME: slow` 注释。
- 补丁（`tools/ffmpeg/aaccoder-pow43.diff`）：首次使用 ESC 码本时，用 `ff_thread_once` 预计算 8192 项表，表值就是原表达式的 float 结果。
- 离线结果：同一 FFmpeg 树，补丁前后各测 3 次，总周期 32.55/32.72/32.57 → 28.36/28.26/28.29 Gcyc（-13.2%），输出 AAC 的 md5 相同。
- 服务端结果：每路 104.5 → 97.5–97.9 Mcyc/s（-6.3% 至 -6.7%），与 profile 中 cbrtf 的占比吻合。离线素材 ESC 码本占比更高，所以离线收益更大。
- 打补丁后的热点：search_for_quantizers_twoloop 34%，ESC 13%，UQUAD/UPAIR/SQUAD 各 6–7%。逐条指令看都是平摊的浮点运算，没有第二个同类可优化点。

### R5 libfdk-aac（隔离实验）

- 每路 58 Mcyc/s，比正式版 104.5 低 44%。服务端的 AAC 份额从约 85 Mcyc/s 降到约 38。
- 单 worker 上限从 21 路提高到约 38 路。

## 5. 每项优化的成本变化（服务端，每路）

| 项 | 正式版 L | 补丁版 P | fdk 版 F |
| --- | --- | --- | --- |
| 总周期 | 104.1–105.0 Mcyc/s | 97.4–98.0（-6.4%） | 57.5–59.0（-44%） |
| AAC 编码（按 profile 份额估算） | ≈85 | ≈78 | ≈38 |
| Opus 解码 | ≈6.7 | 不变 | 不变 |
| 其他（SRTP/RTP/H.264/FLV/syscall/拷贝） | ≈13 | 不变 | 不变 |
| PSS（最大持续容量时） | 376 MiB @168 | 404 MiB @184 | 407–411 MiB @300 |
| 每路内存 | ≈2 MiB | 同 | ≈1.3 MiB |
| UDP 丢包（PASS 轮） | 0 | 0 | 0 |
| 每 worker 上下文切换 | 50–260/s（诊断轮） | – | – |

- 放置改动不改变单路成本，只改变分布：A 与 L 在顺序 160 路时分别为 104.8 与 105.0 Mcyc/s。
- 混合下原版每路略低（102），这是因为饱和 worker 丢包、少做了工作，不代表更省。
- 网络：PASS 轮的服务端 UDP 接收无丢包，接收队列峰值低于 50 KB。
- 调度：每个 worker 只有一个线程，不存在跨 worker 调度。

## 9. 尝试与拒绝的方案

| 方案 | 结果 | 处理 |
| --- | --- | --- |
| 按会话数放置 WHEP Pull | 混合流量下容量从约 100 提到 160–168 | **保留，`a636699`** |
| 按实际 CPU 负载放置 | 同内容下每路成本相同，按会话数已达 19/18、20×8 的完全均匀；按 CPU 放置需要采样和反馈状态，没有额外收益 | 未实现 |
| `aac_coder=fast` | 编码 -63%，但真实音乐 NMR 更差、扰动帧接近 100% | 拒绝（降质） |
| 关闭 TNS/PNS/IS，降低 cutoff | 收益为 0–13%，代价是关闭编码工具或收窄带宽 | 拒绝（降质） |
| FFmpeg `-march=x86-64-v3` | -2.0%，输出相同；要求部署机支持 AVX2 | 拒绝（收益太小） |
| FFmpeg cbrtf 查表 | 每路 -6.4%，+16 路，输出逐字节相同 | 隔离实验，建议采用（需重建 FFmpeg） |
| libfdk-aac | 每路 -44%，+132 路，NMR 更好 | 隔离实验，需许可决定 |
| fdk afterburner=0 | 编码再省 2/3，NMR 略差于 ab=1，但仍优于现状 | 只做了离线测量；若采用 fdk，可作为容量与音质之间的可选档位 |
| libopus 解码代替原生解码 | 12.9 vs 9.7 Mcyc/s，更慢 | 拒绝 |
| 单声道源编单声道 | 浏览器源常为单声道内容，可省约一半 AAC 成本。但要可靠判断，需要 sprop-stereo 或 Opus TOC 立体声位；libopus 低码率时会对立体声输入临时单声道编码，误判会把立体声降为单声道 | 未实现，列为后续单独研究 |
| 减少拷贝和分配、SRTP/RTP 优化 | 合计 <5%，每项 1–2% | 不做（收益不抵复杂度） |

## 10. 最终瓶颈与是否继续

- **正式版**：单 worker 上同步的 FFmpeg AAC 编码，每路 85 Mcyc/s。8 核已到 168 路（每 worker 21 路，22 路即饱和），不改依赖就没有大于 5% 的可做项。**建议停止在代码层面继续优化。**
- **下一步收益取决于依赖决定**：
  1. 采用 cbrtf 查表补丁：重建 `~/ffmpeg901`，或升级到包含类似修复的 FFmpeg 版本。+16 路，风险很低。
  2. 采用 libfdk-aac：先做许可与专利评估，再为 media_server 单独构建 LGPL FFmpeg + fdk。+132 路。
     - 如果采用，可同时补偿编码器延迟（输出时间戳减去 `initial_padding`），把音画偏差从 -77 ms 降到约 -35 ms。这对原生 AAC 同样适用，原生可从 -51 ms 降到约 -30 ms。
     - 这一步改变时间线语义，应单独做 A/V 验证。
- **fdk 版的下一个瓶颈**：仍是单 worker CPU（300 路时最忙 0.95）。届时非 AAC 部分约占每路 20 Mcyc/s 的 35%，Opus 解码与网络收发会成为下一批热点。
- **旁路发现（不在本次范围）**：WHEP 播放侧的 egress 转码器建在首个观看连接所在的 worker 上，与本次修复前的拉流是同一类放置问题。
  - 测试台的上游在 250 路时 16 个线程中 4 个打满，其余 0.34。原因是每个测试源占用固定数量的连接，WHEP 连接按周期落到 4 个 worker 上。
  - 生产中，大量 WHEP 观看者会受到同样影响，建议另开任务处理。
