# 全协议混合负载性能分析与优化（2026-10-30）

## 结论

固定 8 个物理核心。三种混合比例下，原始版本与最终版本的容量如下：

- **“最大持续”**：该倍率的全部重复运行都 PASS。
- **“留余量稳定”**：最忙核心不超过约 0.87，即保留约 13% CPU 余量的最高测试点。

PASS 的判定条件：
- 无 UDP 接收丢包；
- 全部观看者就绪且持续推进；
- 实时比不低于 0.99；
- 源和观看者 churn 无失败；
- 四种输出的解码与时间线探测全部通过；
- 资源回收正确。

| 混合 | 版本 | 最大持续：输入源 / 观看者 / Opus→AAC / AAC→Opus egress | 留余量稳定：输入源 / 观看者 / Opus→AAC / AAC→Opus egress |
| --- | --- | --- | --- |
| A 全协议广播 | 原始 | 1.0×：64 / 5800 / 8 / 64 | 1.0×（最忙核 0.83） |
| A | 最终 | 1.05×：65 / 6090 / 8 / 57（另 8 路直通） | 1.05×（0.85） |
| B WebRTC 为主 | 原始 | 1.2×：154 / 1920 / 116 / 154 | 1.1×：141 / 1760 / 106 / 141（0.86） |
| B | 最终 | 1.6×：205 / 2560 / 154 / 51（另 154 路直通） | 1.5×：192 / 2400 / 144 / 48（0.87） |
| C 多源少观看 | 原始 | 2.15×：722 / 1789 / 138 / 138 | 2.0×：672 / 1664 / 128 / 128（0.87） |
| C | 最终 | 2.15×：722 / 1789 / 138 / 138 | 2.0×（0.87） |

各混合的协议组成见“混合负载定义”。

**整体收益与来源**
- **B（WebRTC 为主）：** 最大持续容量 +33%（1.2×→1.6×），留余量容量 +36%（1.1×→1.5×）。
  - 收益几乎全部来自 WHIP/WHEP Pull 源向 WHEP 观众直通原始 Opus（`3b6c0bd`），省去 Opus→AAC→Opus 的二次转码。
  - 同负载 1.25× 下：服务端 cycles −22%，指令 −29%，控制请求 p99 从约 10 ms 降至 4.4 ms。
- **A（全协议广播）：** 约 +5%（1.0×→1.05×），在边界噪声范围内。
  - 来自 worker 租约放置（`1e2799b`）带来的负载均衡，以及 A 中 8 个 WebRTC 源的直通。
- **C（多源少观看）：** 无变化。
  - C 的 WHEP 观众全部落在 RTMP（AAC）源上，没有可直通的观众。
  - 其他转码均为协议所必需（AAC 源→WHEP 需要 Opus，Opus 源→FLV/RTMP 需要 AAC）。
- **WHEP 音画同步：** 修复了原有缺陷（`21c51b5`）。原始版本的 WHEP 输出音画偏差在 −52…+8 ms 间波动，并伴随音频缺口和解码告警；最终版本恒定在 1–4 ms。这一项不影响路数，是质量修复。

**当前首要限制因素**

| 混合 | 首要限制 | 主要开销 |
| --- | --- | --- |
| A | 内核网络栈 | 内核占 56% 采样，其中含环回下客户端接收处理计入服务端核心的测试结构因素，见“瓶颈”。超出边界时首先表现为 UDP 接收丢包 |
| B | 协议必需的音频转码与网络发送 | fdk AAC 14%、libopus 10%、SRTP 6%、内核 39% |
| C | 协议必需的音频转码 | libopus 26%、fdk AAC 13% |

8 个 worker 在三种混合下都已均衡，最忙线程与最闲线程相差 ≤0.05。继续调整放置没有收益。

**能否进一步优化**
- **按需转码：** 有观众时才启动 Opus→AAC。本测试的所有源都有 AAC 观众，测不出收益，因此只记录为方向。
- **libopus complexity 7：** 编码 CPU −17…−25%，但 128 kbps 立体声 SNR 下降 0.05–0.17 dB，违反“不降低音频质量”，因此未采用。
- **UDP sendmmsg/GSO 批量发送：** 只影响 A 中 UDP 输出的一部分。

以上都不能在不降低质量的前提下带来与 B 同量级的收益。

## 2. 混合负载定义

倍率 s 时各项数量按比例取整，下表为 1.0× 时的数量。

| 混合 | 输入 | 输出 | 资源竞争特点 |
| --- | --- | --- | --- |
| A 全协议广播 | rtmp 24、rtsp_tcp 8、rtsp_udp 8、gb_udp 8、rtmp_pull 4、rtsp_pull 4、whip 4、whep_pull 4，共 64 | rtmp 1500、rtsp 1500、flv 1500、hls 200、whep 400、gb_udp 500、gb_tcp_active 200，共 5800 | 单源多观看，TCP/UDP 发送为主 |
| B WebRTC 为主 | whip 48、whep_pull 48、rtmp 32，共 128 | whep 640、flv 640、rtmp 320，共 1600 | Opus→AAC、AAC→Opus 转码与 SRTP |
| C 多源少观看 | rtmp 96、rtsp_tcp 32、rtsp_udp 32、gb_udp 64、gb_tcp_passive 16、rtsp_pull 16、rtmp_pull 16、whip 32、whep_pull 32，共 336 | flv 336、rtmp 336、hls 32、whep 64、gb_udp 64，共 832 | 大量输入与解复用，每个转码器只服务少数观众 |

**观看者分配**
- 第 i 个某协议观看者订阅 `sources[i % N]`，源按上表输入顺序排列。
- A、B 的 WHEP 观看数大于源数，每个源都有 WHEP 观众。
- C 的 WHEP 观众只覆盖前 64·s 个源，全部是 RTMP 源。
- 因此 C 有 64·s 个 AAC→Opus egress，每个只有 1 个观众；WHIP/WHEP Pull 源只有 FLV/RTMP 观众。

**稳态期间的持续业务操作**（三种混合相同）
- `--source-churn 20`：每 20 s 新建并删除一个 RTMP 发布和一个主动拉流。
- `--churn rtmp:100`：每轮新建并删除 100 个 RTMP 观看。
- `--control-probe-ms 200`：每 200 ms 一次控制请求。
- `--viewer-interleave-seed 11 --pull-interleave-seed 11`：观看者、拉流交错创建。
- 窗口结束后通过控制接口删除全部源，检查 FD、PSS 和遗留接收器。

**素材**
- 负载：`perf_fixture_720p30.flv`（H.264 720p30 + AAC 48 kHz 立体声，约 2.15 Mbit/s）与 `perf_fixture_whip.mkv`（同视频 + Opus）。
- 音画同步：`avsync_720p30.flv`、`avsync_whip.mkv`（每秒闪光/蜂鸣标记），分辨率、帧率、编码与负载素材一致，码率略低。
- 帧率、分辨率与音频参数未作任何改动。

**上游结构**
- 拉流与 GB 输入来自同机另一个 media_server（固定二进制，16 worker，运行在客户端核心上）。
- 64 个上游源由全部主动拉流和 GB 输入轮流共享（`--upstream-sources 64`），不等同于完全独立的上游源。

## 3. 测试环境

**硬件与系统**
- 测试机 `<TEST_HOST>`：Intel Xeon Silver 4216，单路 16 核 32 线程，93 GiB 内存。
- Linux 6.8.0-84，`schedutil` 调频。

**CPU 分配**
- 服务端独占物理核 0–7（`--threads 8`）；SMT 兄弟线程 16–23 空闲，每轮记录其占用均 <0.02。
- 客户端、上游与分析工具使用 8–15、24–31。
- 服务端与客户端在同一网络命名空间内，通过环回地址 198.19.0.10/11 通信。

**测量方法**
- 预热 15 s 后记录 60 s 窗口，倍率递增搜索边界，边界附近重复 2–5 次。
- 关键 A/B 采用 ABBA 交替。
- cycles 和 instructions 来自 `perf stat`。
- 由于 `schedutil`，busy 核数会随频率变化，比较时以 cycles 为准（见 [performance.md](../../performance.md)）。

**测试机设置变更**
- 本轮只修改了测试命名空间内的 `net.ipv4.ip_local_port_range`：32768–60999 → 32768–49151。
- 未修改全局 sysctl，也未增加核心。
- 原因：上游与数千个客户端共用一个地址，内核分配的临时端口与 media_server 的媒体端口池（49152–65535）重叠。上游创建 WHEP Pull 会话时 UDP bind 返回 EADDRINUSE，会话以 500 失败，B 1.5× 以上无法完成准备。
- 修改后重新测量了全部 B 数据，以及其后的 A、C 重复。
- 部署时应保证媒体端口范围与临时端口范围不重叠；服务端遇到被占用端口时不会换一个端口重试，见第 15 节。

## 6. 发现的实际瓶颈

**1. 三个独立的 worker 选择器互相叠加**
- 原始版本中，WHIP、WHEP Pull 各自按“会话最少”选择 worker，两个计数互不可见。
- 在 A 中，4 个 WHIP 与 4 个 WHEP Pull 都在平局时选中 worker 0–3：
  - 这 4 个 worker 的 UDP `recvfrom` 次数为其余 worker 的约 2.7 倍（4800 对 1800）；
  - schedstat CPU 高 7.5%；
  - TCP 连接数相同。
- 证据：每线程的 socket 归属与 schedstat 采样（`fdmap`）。

**2. 二次音频转码（B 的首要瓶颈）**
- WHIP/WHEP Pull 的 Opus 先解码再编为 AAC 进入内部流；WHEP 观众订阅时又经共享 egress 把 AAC 编回 Opus。
- B 原始 1.0× 的采样中 libopus 编码占 28%。
- 每个 WHIP 源的 WHEP 观众只需要源里原本就有的 Opus。

**3. WHEP SR 的 NTP 取自发送时刻**
- ireader 的 SR 以“最后发送包的 RTP 时间戳 + 墙钟外推”生成（`rtcp-sr.c`）。
- 接收端按 SR 对齐音视频，因此视频、音频两条轨在服务端内部的投递延迟差（例如经过转码器的音频晚到）会直接变成音画偏差。
- 原始版本 WHEP 输出：偏差在 −52…+8 ms 间波动，伴有 2–6 个音频缺口和 6–48 个解码告警；同源 FLV 输出恒定 ±5 ms。
- 这是正确性缺陷，同时也意味着原有的 WHEP 输出达不到“音画同步不持续漂移”的要求。

**4. 内核网络栈（A 的首要瓶颈）**
- A 中内核占 56%，主要是 `tcp_sendmsg`、`__tcp_transmit_skb`、`ep_poll_callback`、`__inet_lookup_established`、`tcp_v4_rcv`、`net_rx_action`。
- 服务端与客户端在同一命名空间内经环回通信，接收方协议栈的处理（`tcp_v4_rcv`、`tcp_rcv_established`、`net_rx_action`）以软中断形式在发送方 CPU 上执行，计入服务端核心。真实网卡场景下这部分由客户端机器承担，因此 A 的绝对容量偏保守。
- TCP 输出已按队列合并为 gather write（`tcp_transport::post_write`），用户态发送路径（`tcp_transport::*`）合计约 1.7%。
- A 超出边界时首先出现 UDP 接收丢包（rtsp_udp、gb_udp 输入），此时最忙核约 0.87–0.9，所以 A 留余量与最大持续几乎重合。

**5. 测试结构：端口重叠**
- 见第 3 节。只影响压测上游，服务端在本测试结构下没有出现该错误。

## 7. 优化方案与实验过程

### 7.1 worker 租约（`1e2799b`，接受）

**实现**
- `worker_pool::lease()` 在一把互斥锁下选择当前租约数最少的 worker 并计数。
- 返回 move-only 的 `worker_lease`，析构时释放计数。
- WHIP 会话、WHEP Pull 会话和共享音频 egress 都持有租约，删除各自重复的最少选择和计数代码。
- TCP accept 的轮询与 HTTP 会话所在 worker 不变。

**ABBA**（m10/m11/m12/m13 为 A 1.1×；m15/m16/m17/m18 为 B 1.25×，原始/租约/租约/原始）

| 指标 | A 原始 | A 租约 | B 原始 | B 租约 |
| --- | --- | --- | --- | --- |
| worker 线程最高–最低 | 0.96–0.87、0.95–0.86 | 0.95–0.88、0.94–0.88 | 0.99–0.93、1.00–0.94 | 0.97–0.96、0.98–0.95 |
| 最忙核 | 0.93、0.92 | 0.91、0.91 | 0.97、0.97 | 0.97、0.97 |
| Gcycles/s | 18.38、18.38 | 18.46、18.45 | 18.07、18.00 | 18.09、18.09 |
| 结果 | FAIL（丢包 56、1） | FAIL（丢包 166、60） | PASS×2 | PASS×2 |

结论：
- 分布更均匀，总 cycles 不变。
- A 1.1× 在两种版本下都因 UDP 丢包失败，B 1.25× 都通过，单独看不出容量差异。
- 接受的理由：删除了两套重复的放置逻辑，统一为一个可推理的机制，并消除平局叠加。后续的直通改动在此基础上实现。

### 7.2 WHEP SR 媒体时间线（`21c51b5`，接受，缺陷修复）

**实现**
- `webrtc_packetizer` 在会话首帧到达时记录“墙钟 − pts”作为起点，并记录每条轨最近发出包的 RTP 时间戳与 pts。
- 发出 SR 前，把 NTP 字段改写为“起点 + 该 SR 的 RTP 时间戳对应的 pts”。
- RTP 时间戳、包内容与发送节奏都不变。

**验证**（单流音画同步，每轮 12 个闪光/蜂鸣标记；偏差 = 闪光 − 蜂鸣）

| 源 → WHEP | 修复前 | 修复后 |
| --- | --- | --- |
| RTMP AAC 源（经 egress 转 Opus） | −36…−1 ms，3 个缺口，25 个告警 | 2.0 / 1.0 ms，0 缺口，0 告警 |
| RTMP 内 Opus 源（原有直通） | −24…−3.3 ms | 2.7 / 2.7 ms |
| WHIP 源（直通，见 7.3） | 恒定 +35.7 ms | −4.3 / −4.3 ms |
| 参考：同源 FLV 输出 | −5.5 / 2.5 / 2.7 ms | — |

素材本身的偏差为 0 ms（WHIP mkv）和 1.2 ms（FLV）。

**回放工具的启动伪像**
- WHIP 源的第一帧视频在媒体时间上比第一帧音频早 41 ms。ffmpeg 的 RTP 解复用按 SR 同步后，会把开头两帧视频的时间戳钳到同一个值。
- 服务端发出的 RTP 时间戳单调。
- 因此回放工具（`fa901c4`）改为用 dump 中的 RTP 时间戳判定时间线回退，录制文件自身的计数保留为 `recorded_video_pts_backward`。

### 7.3 Opus 直通（`3b6c0bd`，接受）

**实现**
- WHIP 接收器（WHEP Pull 复用它）在 AAC 内部流之外，再发布一个只含视频和原始 Opus 的伴随流，通过 `media_stream::opus_stream()` 关联。
- WHEP 观众的 offer 满足直通条件时，订阅伴随流；不满足时仍走 AAC 流和共享 egress。
- 直通条件：立体声源要求 `stereo=1`；`maxplaybackrate`、`maxaveragebitrate`、`maxptime` 不加限制。
- 伴随流随主流结束；`stream_id` 不变，不进入注册表。
- Opus→AAC 转码保留，供 FLV/RTMP/RTSP/HLS/GB 观众使用。

**ABBA**（B 1.25×）
- 运行：m25 原始(租约)、m27 直通、m28 原始(租约)，补充 cap-B-p-1.25-r2 与 cap-B-m2-1.25-r3。
- m26 因第 3 节的端口问题没有完成准备，不计入。

| --- | --- | --- |
| busy 核 | 7.75、7.76、7.71 | 6.03、6.01 |
| 最忙核 | 0.98、0.98、0.97 | 0.76、0.76 |
| Gcycles/s | 18.12、18.14、18.03 | 14.22、14.12 |

结果：cycles −22%，指令 −29%。容量搜索中 B 由 1.2× 提高到 1.6×。

**正确性**
- 音画同步：B 1.6× 负载下 WHEP 输出偏差恒定 −4.3 ms，0 缺口、0 告警。
- 直通会原样保留源的时间戳。WHIP 发布端 `-stream_loop` 在素材循环接缝处，音频比格式时长短约 21 ms，直通输出中可见一次 41 ms 的 RTP 时间戳跳变（1968 = 2×960 + 48），随后有两次 ±1 ms。序列号连续，没有丢包。
- 原 egress 路径从样本数重建时间线，因此看不到这个缺口。FLV 素材在接缝处同样有 33 ms 的音频缺口，两种版本下的 FLV/RTMP/RTSP/HLS 输出都能看到。这是素材循环的属性，不是服务端缺陷。

### 7.4 否决与未实施

| 方案 | 结论 | 依据 |
| --- | --- | --- |
| libopus complexity 7（egress 编码） | 否决 | 6 段 48 kHz 立体声 30 s 素材的测量见下表。complexity 8–10 输出逐比特相同；7 是第一个有 CPU 收益的档位，但有可测的质量下降，违反质量约束 |
| 放宽直通条件，允许单声道 offer 接收立体声 Opus | 未实施 | 违反 RFC 7587 的 `stereo` 语义；本轮负载的浏览器类 offer 已满足条件，无需放宽 |
| 统一 worker 调度器，按实际成本分配 | 未实施 | 租约之后三种混合的 worker 相差 ≤0.05，继续调整分配没有空间 |
| UDP sendmmsg/GSO | 未实施 | A 中 UDP 相关内核符号合计约 1.8%，主体是 TCP 和环回接收，预期收益小于边界噪声 |

**回放工具的两个伪像**
- **B 原始 1.1× r2 录到 0 帧：** 固定回放端口 46000 落在临时端口范围内，与客户端套接字冲突。离线重放同一 dump 得到 749 帧。`5491796` 改为自动选择空闲端口，重跑 r3 PASS。
- **B 最终版本负载运行中的 WHEP 录制，每轮一个 80 ms 音频缺口：** 修正端口后仍然出现。缺口位于录制的第一个音频包与第二个包之间（pts 0 → 0.100），与 7.2 中视频首帧被钳位属于同一类：ffmpeg 按首个 SR 同步时，把开头的包钳到起点。

  - 判定依据改用 dump 本身，以 [whep_dump_rtp.py](whep_dump_rtp.py) 检查：25 s 窗口内 Opus RTP 序列号连续，时间戳步长恒为 960；唯一的不规则步长是 7.3 所述的素材循环接缝（约第 56 s）。
- **WHEP 音频到达间隔：** AAC→Opus egress 路径两种版本相近，p99 约 45–56 ms，最大 80–90 ms，来自 AAC 1024 样本帧与 Opus 960 样本帧的成批换算。直通路径 p99 为 22 ms。到达抖动由接收端抖动缓冲吸收，时间戳不受影响。

## 15. 值得继续研究的方向

1. **媒体端口与临时端口重叠**
   - 默认媒体端口池 49152–65535 与 Linux 默认临时端口 32768–60999 重叠。
   - 服务端主动拉流、HTTP 回调等出站连接占用的端口，可能被端口池再次分配；UDP bind 失败后，会话直接以 500 失败，不会换一个端口重试。
   - 本轮只在压测上游中触发。修复方式可以是 bind 失败时释放并取下一个端口，或在部署文档中要求不重叠。属于服务端行为改动，需要另行决定。
2. **按需 Opus→AAC**：只有 WHEP 观众的 WebRTC 源可省去全部音频转码。需要在 AAC 观众出现时启动转码，并处理首帧延迟与时间线衔接，复杂度明显高于直通。
3. **A 的内核开销**：需要双机真实网卡测试，才能区分服务端发送和环回接收各自的份额。在此之前，任何用户态发送优化都难以测出收益。
4. **ASan 下的 SRTP replay_fail 偶发**：原有问题，见第 14 节。

没有发现需要立即处理的 CPU 热点。三种混合的剩余开销，都是协议必需的转码、加密和网络发送。
