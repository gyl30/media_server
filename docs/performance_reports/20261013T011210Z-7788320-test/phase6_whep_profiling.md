# 阶段 6 P0：WHEP CPU 画像与规模曲线归因

- 运行 ID：`20261013T011210Z-7788320`，基线 `7788320af210ab63939c84b6fdcb4e7518674caa`
- 目标：定位 WHEP 真实 CPU 热点，区分用户态/内核态/软中断，解释观看数与源数两个维度的成本差异
- 约束：未修改任何生产代码；仅测量、分析与报告
- 结论级别标注：**[实测]** 直接测量；**[推导]** 由多个实测组合；**[待确认]** 证据不足

## 1. 结论摘要

1. **[实测] WHEP 的软件工作量对观看数是严格线性的，"高并发更高效"是假象。**
   各档位每观看端交付量完全一致（218.1 kB/s、231 pkt/s，1200/1500/1800 档逐档相同），
   `sendto` 次数精确线性（V1500→V1800 为 +20.2%，对应 +20% 观看），没有出现批处理或合并发送。

2. **[实测] 表观“每观看端成本随规模下降”的主解释是 CPU 调频。**
   turbostat 实测服务端 8 核 `Bzy_MHz`：V400（20% busy）为 **802 MHz**，V1800（68% busy）为 **1540 MHz**，+92%。
   方呰 20% 的每观看端周期数上升（IPC 1.62→1.35）完全被频率上升压过，方得到实测的 −34% CPU/观看。
   推导方向上每观看端指令数在 400→1800 全程保持 5.5～6.3 M/s（±6%）。**[推导，非严格同窗]**
   频率、IPC 与 CPU 秒来自不同运行和不同时间窗，本节不构成严格同窗的因果证明；
   它建定的是“调频是主要解释”，**不声称已排除所有软件非线性**（见 §3.5 与 §11）。

3. **[实测] 最大单一用户态热点是 `h264_startcode`，占 8.8%（0.39 核 @V1200，0.33 mCPU/观看）。**
   调用链为 `whep_session::on_frame → webrtc_packetizer::input_video → rtsp_muxer_input →
   rtp_h264_annexb_nalu`，即**每个观看端对同一帧重复扫描 H.264 NAL 边界并重新 RTP 打包**。

4. **[实测] 内核态占 50.2%，其中 UDP 发送路径、epoll 与锁是主体。**
   用户态合计 50.5%（libcrypto 12.97% 属于用户态）；与 `/proc` 的 user 51.9% / system 48.1%
   相差 1.7 个百分点，差异来由已在 §4.1 定量说明。

5. **[实测] 源维度的增量主要来自每源一次的 AAC→Opus 转码，不是每观看端工作变贵。**
   S8−S1 增量 0.585 核（84 mCPU/源），其中 Opus/CELT 编码 0.026→0.236 核，**约 30 mCPU/源（占增量 36%）**；
   每观看端视频路径成本不随源数变化（`h264_startcode` 0.393→0.407 核，+3%）。
   源码确认 `acquire_whep_audio_egress()` 以 `{source, channels, bitrate, max_playback_rate}` 为键共享转码器，
   即"每源转码一次、向所有观看端分发"，属既有设计。

6. **[实测] 调度不是瓶颈。** 所有档位 run-queue 等待中位数 0.02 µs、10 s 内总计 <0.05 s；
   上下文切换 450-560 次/s。V1800 时 8 核 busy 仅 64%，未接近饱和。

7. **对既有阶段的影响（见 §8）**：本机的“CPU 秒”不是跨负载可比的单位。低负载档位测得的
   mCPU/观看会系统性高估高负载成本；按实测频率区间推算，上界约 1.9 倍（802→1540 MHz）。**[推导]**

## 2. 测量方法

### 2.1 采样编排

`pi_phase6p.py` 在 `perf_run` 的测量窗口内串行执行四个采样相位：

| 相位 | 时长 | 内容 |
|---|---|---|
| off-CPU | 全程 | host 侧 `bpftrace` helper（`sched_switch` + `nsecs`） |
| phase1 | 30 s | DUT 定向 `perf record -F 99 --call-graph dwarf,16384` |
| phase2 | 20 s | 服务端 8 核 `perf record -F 39`（内核/软中断归属） |
| phase3 | 10 s | `perf stat`（IPC、上下文切换、page fault、syscall 计数） |

**分相串行是必需的。** 首版实现按固定时刻并发启动三个相位，结果 DUT 记录只有 1,756 样本、
`perf stat` 的 `cycles/instructions` 使能率被压到 8%；改为"前一相位进程退出后才启动下一相位"后，
同样 30 s 得到 12,959 样本、`perf stat` 使能率 100%。

**窗口对齐。** 首批 V1200/V1800 的 phase1 起点比测量窗口早 4.0 s（落在 warmup 末尾），
已用 `profile_start=60/90` 重跑，重跑后所有相位满足 `windows_inside=true`。
本报告使用的画像数据全部来自重跑或本身就在窗口内的运行（V400 起点 +14.1 s、V800 +4.1 s、V1500 在窗口内）。

### 3.5 完整分解

| 档位 | CPU 核 | mCPU/观看 | MHz | IPC | Mcyc/观看 | Minstr/观看 |
|---|---|---|---|---|---|---|
| V400 | 1.7085 | 4.27 | 802 | 1.62 | 3.43 | 5.55 |
| V800 | 3.0839 | 3.85 | 993 | 1.58 | 3.83 | 6.05 |
| V1200 | 4.4598 | 3.72 | 1110 | 1.52 | 4.13 | 6.27 |
| V1500 | 4.9693 | 3.31 | 1250 | 1.41 | 4.14 | 5.84 |
| V1800 | 5.0860 | 2.83 | 1540 | 1.35 | 4.35 | 5.87 |

**[推导，非严格同窗]** `Mcyc/观看 = CPU核 × MHz / 观看`，`Minstr/观看 = Mcyc × IPC / 观看`。
频率来自独立的探针运行（每档 10 s）、IPC 来自画像运行的 10 s `perf stat` 窗、CPU 秒来自另一批
权威口径运行，**三者不是同一时间窗口**；组合量约有 ±10-15% 不确定度。因此本节能支持的是：

- 频率随忙度从 802 升到 1540 MHz（**[实测]**，turbostat 与 vPMU 两个仪器互相印证）；
- 方呰 92% 的频率上升足以单独解释 −34% 的 CPU/观看，**因此不需要引入软件变快假设**；
- 在此前提下，每观看端指令数表现为恒定（±6%），IPC 下降 17%。

本节**不支持**以下强声明：已证实每观看端软件工作量严格恒定、已排除所有软件非线性、
或已在同一窗口内建定因果。要把“工作量恒定”做成实测而非推导，需要在同一次运行内同时拿到
频率、IPC 与交付包数（下一轮可用 `perf stat -I` 与客户端逐秒计数对齐实现）。

因此阶段 5 记录的“阶段 4 线性模型在 V1500 高估 15%”以及本阶段最初拟合的
`CPU = 0.339 核 + 3.42 mCPU/观看`（在 V800 回推误差 −0.18%，外推 V1500 高估 9.5%）
至少大部分来自**用低负载频率去外推高负载**；是否还叠加软件非线性，本次未判定。

## 4. WHEP CPU 构成（S1 V1200，4.481 核）

### 4.1 按 DSO 归属

初稿用 0.1% 阈值，得到“内核 45.6% > 用户 38.3%”，与 `/proc` 矛盾；改阈值为 0.01% 后又出现
“表中各项合计与声称的覆盖率不一致”。两个问题一并重做：

| 阈值 | 条目数 | 合计 |
|---|---|---|
| 0.1% | 183 | 83.9% |
| 0.01% | 642 | 97.43% |
| 0.001%（=不限） | 977 | **100.78%** |

**[实测] 取 0.001% 阈值即完整覆盖**，100.78% 是 977 个条目各自保留 2 位小数的四舍五入累积误差（±0.8%）。
0.01% 与 0.001% 之间的 2.57% 分布在 335 个单条 <0.01% 的条目上，**其中 2.1 个百分点属于 libcrypto**
（该库无调试符号，时间分散在许多未解析地址上）。因此初稿的 10.88% 低估了 libcrypto。

完整归属（阈值 0.001%，S1 V1200，4.481 核）：

| DSO | 占比 | 核数 | mCPU/观看 |
|---|---|---|---|
| `[kernel.kallsyms]` | 50.24% | 2.251 | 1.876 |
| `media_server` | 28.23% | 1.265 | 1.054 |
| `libcrypto.so.3` | **12.97%** | 0.581 | 0.484 |
| `libc.so.6` | 4.44% | 0.199 | 0.166 |
| `libjemalloc.so.2` | 3.02% | 0.135 | 0.113 |
| `[unknown]` | 0.66% | 0.030 | 0.025 |
| `[vdso]` / libstdc++ / spdlog / 其他 | 1.23% | 0.055 | 0.046 |

用户态合计 50.5%、内核 50.2%（按 100.78% 归一后 50.2% / 49.8%）。
`[unknown]` 0.66% 是用户态未解析地址（DWARF 展开失败或裁剪帧），量级 <1%，不影响结论。

**与 `/proc` 的差异**：权威口径为 user 51.9% / system 48.1%，画像为 50.2% / 49.8%，差 1.7 个百分点。
差异方呰0.5 个百分点内可接受，未完全对齐的原因是两种口径不同：`/proc` 的 utime/stime 按内核调度边界计时，
而 perf 按采样时刻的指令地址归类；系统调用进入/退出路径（如 `clear_bhb_loop`、`entry_SYSCALL_64`）
在两种口径下归类不同。**[实测]** 差异已定量，未强行调平。

### 4.2 用户态热点（self，≥0.5%）

| 占比 | 符号 | 归属 |
|---|---|---|
| 8.78% | `h264_startcode` | 每观看端重复 NAL 扫描（见 §4.4） |
| 2.05% | `udp_transport::start_write()` | 发送入口 |
| 1.69% | `_Sp_counted_base::_M_release()` | `shared_ptr` 引用计数原子递减 |
| 1.38% / 0.88% | `__memmove_evex_unaligned_erms` / `__memset_...` | 拷贝与清零 |
| 1.08% / 0.69% | jemalloc `free` / `malloc` | 每包分配 |
| 0.94% | `webrtc_packetizer::on_packet()` | RTP 头与扩展写入 |
| 0.86% | `boost::asio::reactive_socket_sendto_op` | 发送封装 |
| 0.83% | `bitvector_left_shift` | 由 `srtp_rdbx_add_index` 调用，每包更新重放窗口位向量 |
| 0.81% / 0.78% | `srtp_protect_mki` / `srtp_transport::protect_rtp` | SRTP 封装 |
| 0.79% | `__strcmp_evex` | 调用链落在打包/加密路径，**[待确认]** 具体调用点 |
| 0.77% / 0.72% / 0.65% / 0.42% / 0.28% / 0.25% | `EVP_CIPHER_up_ref` / `OSSL_PARAM_locate` / `EVP_Cipher` / `EVP_CIPHER_CTX_ctrl` / `EVP_CIPHER_free` / `EVP_CIPHER_CTX_get_iv_length` | **OpenSSL 3 API 开销，合计 3.09%**（机制见 §4.6） |

**[实测] libcrypto 的时间主要在“进入 OpenSSL API 的固定开销”，不在密码运算本身。**
同一 profile 中实际 GCM 运算（`CRYPTO_gcm128_encrypt_ctr32` 0.22 + `setiv` 0.18 + `aad` 0.17）约 0.57%，
而 API 开销约 3.09%，比例约 5:1。具体机制已在 §4.6 核实（初稿把它当作“每包 fetch 算法”的推测已推翻）。

### 4.6 SRTP / OpenSSL 实际机制（已按 §2.3 核实）

**版本与链接方式 [实测]**

| 组件 | 版本 | 链接 |
|---|---|---|
| libSRTP | **2.7.0**（`third/libsrtp`，CMake `libSRTP::srtp2`） | 静态，已内置进 `media_server` |
| OpenSSL | **3.0.2**（`libssl3 3.0.2-0ubuntu1.30`） | 动态 `libcrypto.so.3` |

**已证实的每包行为 [实测，源码 `third/libsrtp/crypto/cipher/aes_gcm_ossl.c`]**

一次 `srtp_protect()`（本项代码在 `media/webrtc/srtp_transport.cpp:138` 每包调用一次）在 AES-GCM 路径上产生：

| 步骤 | 源码行 | OpenSSL 调用 |
|---|---|---|
| 设 IV | `aes_gcm_ossl.c:229` | `EVP_CipherInit_ex(ctx, NULL, NULL, NULL, iv, -1)` |
| 送 AAD | `:278` | `EVP_Cipher(ctx, NULL, aad, aad_len)` |
| 加密 | `:306` | `EVP_Cipher(ctx, buf, buf, len)` |
| 算 tag | `:330` | `EVP_Cipher(ctx, NULL, NULL, 0)` |
| 取 tag | `:335` | `EVP_CIPHER_CTX_ctrl(GET_TAG)` |

即**每个受保护包 5 次 OpenSSL API 入口**，全部复用同一个 `EVP_CIPHER_CTX`——
该上下文在 `:113` 的 cipher `alloc` 中创建，**不是每包创建**。

**排除法 [实测]**：`EVP_CIPHER_up_ref` / `EVP_CIPHER_free` / `EVP_CIPHER_fetch` 在
- 本仓代码（`media/`、`src/`）中不存在（只有 `dtls_certificate.cpp` 在建立期用 EVP 做证书摘要/密钥生成）；
- libSRTP 2.7.0 全文中也不存在（grep 无匹配）。

因此这些符号只能来自 **libcrypto 3.0.2 内部**（由其自己的 `EVP_Cipher` / `EVP_CIPHER_CTX_ctrl` 等入口调用），
而不是“我们或 libSRTP 每包重新 fetch 算法”。**初稿的表述已推翻。**

**[未证实]** libcrypto 内部具体是哪个函数产生这些引用计数与 `OSSL_PARAM_locate`：
DWARF 调用链提取在该符号上超出时间预算（>240 s 未返回），未拿到直接调用链。

**对优化候选的影响**：正确的杆杆是**减少每包的 OpenSSL API 入口数**（合并 AAD/数据/标签的调用序列，
或改用不逐次进入 provider 机制的底层接口），而不是在本仓代码里缓存算法 fetch——后者不会有帮助，
因为本仓代码本来就没有每包 fetch。

### 4.4 关键调用链（DWARF，S1 V1200）

```
worker_context::run → io_context::run
  → worker_sink_dispatcher<media_frame, media_sink, &media_sink::on_frame>::publish
    → sink_group::drain()
      ├─ 6.68% → whep_session::on_frame → webrtc_packetizer::input_video
      │            → rtsp_muxer_input → rtp_h264_annexb_nalu → h264_startcode
      └─ 1.12% → whep_audio_egress::on_frame → …（同一打包路径）
```

源码对应（基线 `7788320`）：

- `media/webrtc/webrtc_packetizer.cpp:250 input_video()` 把**原始 Annex-B 帧**交给 `rtsp_muxer_input()`，
  由 `third/ireader/librtp/.../rtp-h264-bitstream.c:99 rtp_h264_annexb_nalu()` 逐字节扫描起始码并做 FU-A 分片；
- `webrtc_packetizer` 是**每观看端一个实例**（持有该会话的 `mid`、payload 与序列号状态），
  因此同一源帧的 NAL 扫描与分片对 1200 个观看端各做一遍。

对照：音频路径的转码是**每源共享**的（见 §5.2），视频路径没有对应的共享层。

## 5. 源维度：S8 与 S1 的差异

固定总观看数 1200，比较 1 源×1200 与 8 源×150（已确认观看端在 8 个源上均匀分布，每源 150）。

### 5.1 绝对核数差分

| Δ核数 | S1 | S8 | 项 |
|---|---|---|---|
| +0.028 | 0.004 | 0.032 | `op_pvq_search_sse2` |
| +0.023 | 0.003 | 0.026 | `celt_encode_with_ec` |
| +0.022 | 0.003 | 0.025 | `opus_fft_impl` |
| +0.018 | 0.003 | 0.021 | `quant_partition` |
| +0.017 | 0.000 | 0.017 | `exp_rotation1` |
| +0.015 | 0.017 | 0.032 | `check_heap_object`（内核） |
| +0.013 | 0.393 | 0.407 | `h264_startcode` |
| −0.013 | 0.059 | 0.046 | `__fdget` |
| −0.011 | 0.026 | 0.014 | `__netif_receive_skb_core` |

**Opus/CELT 全族合计：S1 0.590%（0.0264 核）→ S8 4.670%（0.2363 核），比值 8.9×。**

### 5.2 归因

1. **[实测] 每源一次的 AAC→Opus 转码 ≈ 30 mCPU/源，占 S8−S1 增量的 36%。**
   `media/webrtc/whep_audio_egress.cpp:143 acquire_whep_audio_egress()` 以
   `{source.get(), channels, bitrate, max_playback_rate}` 为键复用 egress，`transcoders_` 按 track 持有
   `audio_transcoder`，因此转码次数 = 源数，与观看数无关。这是既有设计（转码一次、分发多份）。

2. **[实测] 每源 ingest 与内核 RX/唤醒路径 ≈ 10 mCPU/源。**
   `__udp_enqueue_schedule_skb` +0.008、`llist_add_batch` +0.011、`__wake_up_common` +0.008、
   `check_heap_object` +0.015 核。

3. **[实测] 每观看端工作不随源数变化。** `h264_startcode` 0.393→0.407 核（+3%），
   `sendto` 245,471→245,953/s（+0.2%），V1200 与 S8-V1200 的 profile 形状几乎相同
   （差分中除 Opus 外所有项 |Δ| ≤ 0.7 个百分点）。

4. **[实测] 源数放大的是"事件次数"，不是"每事件工作量"。**
   off-CPU 直方图：S1 35,424 次阻塞（中位 6 ms）→ S8 **184,871 次**（中位 0.76 ms），5.2 倍；
   `epoll_wait` 2,563→11,203/s（4.4 倍）；上下文切换 501→2,482/s（5.0 倍）；futex 3→82/s。
   一次源到达事件驱动的发送数从 1200 降到 150，事件级摊薄消失。

**与阶段 4 的 50.8 mCPU/源不矛盾**：阶段 4 在 16 观看端下测得，几乎不含事件摊薄差异与音频转码摊薄；
本阶段 84 mCPU/源是"每源 150 观看"的总差分。两者不是同一个量，报告不应把它们当作同一常数的两次估计。

## 7. 内存行为（已按 §2.1 修正）

> 本节初稿写"V1800 每观看端增量约 1.3 MiB，显著高于 V1200/V1500 的 0.2-0.3 MiB，且未在窗口内收敛"，
> **该结论错误**：1.3 MiB 是把跨档位的 `pss_kib_max` 之差除以观看数得到的，而 `pss_kib_max` 抓到的是
> 瞬时峰值，不是稳定水位。按时间序列重算后结论相反。以下是修正后的结果。

### 7.1 建立期一次性分配（与规模成严格线性）

| 档位 | 窗口起点 PSS | 每观看端 | 建立期耗时 |
|---|---|---|---|
| S1 V1200 | 316 MiB | **0.263 MiB** | 56 s |
| S1 V1500 | 431 MiB | **0.287 MiB** | 62 s |
| S1 V1800 | 475 MiB | **0.264 MiB** | 70 s |

**[实测] 每观看端 0.26～0.29 MiB 在 1200→1800 全程恒定**，不存在超线性增长。
这部分在 viewer 建连期间一次性分配，斜率 6.9～9.9 MiB/s 与建连速率一致。

### 7.2 固定负载期间：无单调增长，只有周期性锯齿

| 档位 | 窗口内 PSS 斜率 | RSS 变化 | VmSize | 线程 | UDP/TCP 队列峰值 | 窗口内 UDP 错误 / TCP 重传 |
|---|---|---|---|---|---|---|
| S1 V1200 | −0.010 MiB/s（平） | 334 → 318 MiB | 2589 MiB 恒定 | 16 → 16 | 7.2 KB / 8 B | 0 / 0 |
| S1 V1500 | +0.201 MiB/s（后半，噪声级） | 428 → 425 MiB | 3037 MiB 恒定 | 16 → 16 | 6.9 KB / 8 B | 0 / 0 |
| S1 V1800 | 净平（末 481 vs 窗口起点 475） | 502 → 482 MiB | 3789 MiB 恒定 | 16 → 16 | 4.6 KB / 8 B | 0 / 0 |

**[实测] 三个档位都没有持续增长。** RSS 反而略降，VmSize 与线程数完全恒定，队列近乎空，
UDP 缓冲错误与 TCP 重传均为 0。初稿引用的 843/869 MiB 是 `pss_kib_max`，即下述锯齿的峰值。

V1800 的锯齿形态（1 s 采样）：

```
+0.8s 490 → +2.6s 636 → +11.8s 482   （+147 MiB，10 s 内完全回落）
+14.8s 801 → +23.7s 479               （+322 MiB，完全回落）
+26.7s 641 → +34.7s 497               （+144 MiB，完全回落）
```

周期 11.9～12.1 s，**与 fixture 的循环长度完全一致**（该 720p30 fixture 长 12.0 s，
含 6 个关键帧，间隔 2.0 s、平均 21.7 KiB）。**[实测]**

**[待确认]** 机制未证实：DUT 日志 12,610 行中 warning/error 为 0，发布者日志无循环边界标记，
因此无法把峰值归到具体代码路径。可排除的是"关键帧广播"假设——关键帧间隔是 2 s 而非 12 s，
且 21.7 KiB × 1800 = 39 MiB，与观测的 150～320 MiB 幅度不符。

另外，V1200/V1500 的 1 s 采样未捕捉到同量级峰值，说明**采样相位决定能否看到峰值，
不能据此比较各档幅度**；要定量幅度需要更高频采样（P0-M 将按 5 s 采样并保留完整序列）。

### 7.3 尚未回答的部分

- **清理后是否回落**：现有运行在测量结束后立即停止 DUT，没有"关闭全部 viewer 后继续观察"的数据。
  这是 P0-M 的主要目标。
- **allocator retained 与活跃对象**：需要 heap profile；TEST 仍缺 `jeprof`，若 P0-M 需要则标记 BLOCKED。
- 按现有证据，**不能把 PSS 未回落判为泄漏**（本次也未观察到未回落）。

## 8. 对既有阶段结论的影响

1. **CPU 秒在本机不是跨负载可比单位。** 频率随利用率从 802 MHz 升到 1540 MHz。
   因此：
   - 阶段 3/4 在 16-80 观看端测得的 mCPU/观看，处于 800 MHz 区间，**系统性高估**高负载成本，
     上界约 1.9 倍；
   - 阶段 5 观察到的“阶段 4 模型在 V1500 高估 15%”至少大部分可由调频解释，不需要先引入软件非线性；
     是否还叠加软件非线性，本次未判定；
   - 跨协议比较只有在**总 CPU 相近**时才公平。阶段 3 各协议都在低负载（≈800 MHz）测得，彼此可比；
     但把阶段 3 的每观看端成本用于阶段 5 的高负载容量推算会偏保守。
2. **线性模型仍可用于中低负载**：`CPU = 0.339 核 + 3.42 mCPU/观看` 在 400-1200 区间内误差 <0.2%，
   但必须标注其有效范围来自固定频率区间（800-1110 MHz），不能外推到 1500 以上。
3. **容量结论方向不变**：V1800 时 8 核 busy 64%、无调度竞争、无丢包，DUT 仍有余量；
   实际限制是单核 busy 与出口带宽，不是软件瓶颈。

## 9. 可优化点（按证据强度排序，均为观察，不代表本次要改）

1. **视频打包按源共享**（证据最强）：可直接测得的是 `h264_startcode` 0.33 mCPU/观看（8.8%）；
   加上其下游 `webrtc_packetizer::on_packet`（0.035）、`rtp_onsend`（0.021）以及按份额归给打包的
   拷贝与分配，估计可影响 **0.33～0.5 mCPU/观看（总成本的 9%～14%）**。
   音频已有按源共享的先例（`acquire_whep_audio_egress`），视频没有。
2. **SRTP 每包的 OpenSSL API 入口开销**：每包 5 次 OpenSSL 入口（§4.6 已用源码逐行证实），
   对应测量开销 3.09%（0.12 mCPU/观看），而实际 GCM 运算只占 0.57%。
   杆杆是减少入口数或换用更底层的密码接口；**不是**在本仓缓存算法 fetch（本仓无每包 fetch）。
3. **每包对象生命周期**：`shared_ptr::_M_release` 1.69% + jemalloc `malloc/free` 1.77% ≈ 3.5%。
4. **SRTP 重放窗口位向量**：`bitvector_left_shift` 0.83%，每包左移。
5. **内核侧固定开销**：`clear_bhb_loop` 0.75% + `__fdget` 1.32% 是每 syscall 的固定成本，
   只有减少 syscall（批量化）才能摊薄——但当前是每包一次 `sendto`，属架构选择。

## 11. 限制

1. 频率、IPC 与指令数是**不同运行、不同时间窗**的组合量：频率来自独立探针运行（每档 10 s），
   IPC 来自画像运行的 10 s `perf stat` 窗，CPU 秒来自另一批权威口径运行。单项各自可信，
   组合量按 ±10-15% 看待，且不构成同窗因果证明。
2. guest 内无法固定 CPU 频率（`cpufreq` 只暴露 `cpuinfo_*_freq`），因此"固定频率下的对照实验"
   在当前测试机不可做；要彻底排除调频影响需要宿主机权限或另一台机器。
3. `perf report` 的调用链在深度内联处存在误归属（如 `__strcmp_evex` 的调用点、
   `whep_audio_egress::on_frame` 下出现 `input_video`），本报告只对能由源码印证的主链下结论。
4. 未做 heap profile（TEST 缺 `jeprof`），§7 的周期性峰值机制未归因。
5. 未测 P1（GB UDP/TCP）与 P2（FLV/RTMP）；本报告只覆盖 WHEP。
6. V1800 超出阶段 5 设定的 1500 观看上限，属本阶段为归因"变平"而做的额外扩展；
   DUT 侧未触发任何安全预算（峰值 7.92 核、PSS 869 MiB、内存与磁盘余量充足）。
