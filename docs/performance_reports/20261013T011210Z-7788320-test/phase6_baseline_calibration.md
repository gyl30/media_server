## 4. 标定方法

**档位**（均为阶段 5 已确认的健康负载，客户端资源有余量）

| 档位 | 协议 | 源 | 观看 | group-size |
| --- | --- | --- | --- | --- |
| whep-s1-1200 | WHEP | 1 | 1200 | 200 |
| whep-s8-1200 | WHEP | 8 | 1200 | 200 |
| gb-udp-1000 | GB28181 UDP | 1 | 1000 | 60 |
| gb-tcpa-1000 | GB28181 TCP 主动 | 1 | 1000 | 60 |
| flv-800 | HTTP-FLV | 1 | 800 | 150 |
| rtmp-800 | RTMP | 1 | 800 | 250 |

**调度**：每档 3 个配对，顺序交替 `A B / B A / A B`（共 36 次），使时间漂移不会单向偏袒某一基线；另加 4 次交叉替换（§6）与 2 次补跑，合计 42 次运行。

**四层 CPU 口径**（`pi_phase6.py`，全部按 `result.json` 的 `requested_window`（CLOCK_MONOTONIC）端点对齐）

1. DUT 进程 CPU —— `perf_run` 在测量窗口首末取值，**权威口径**，未被本脚本改动；
2. DUT user/system —— `/proc/<pid>/stat` 的 `utime/stime` 1 Hz 采样；
3. 每核 busy/user/system/softirq —— `/proc/stat` 每 CPU 字段；
4. softirq 类型归因 —— `/proc/softirqs` 窗口前后差值按 CPU × 类型。

口径 1 与口径 2 相互独立，可交叉校验：冒烟用例中 `perf_run` 报 0.0634 核，独立采样得 user 0.0459 + system 0.0173 = 0.0632 核（差 0.4%）。口径 3 也与口径 1 一致：WHEP 1200 档位 8 核 busy 0.5630 × 8 = 4.50 核，与进程 CPU 4.4976 核相差 0.2%。

**统计定义**（复核后的正式口径，见 §5；分析脚本 `pi_phase6s.py`）

- 原始观测 = `perf_run` 在测量窗口内测得的 DUT 进程 CPU（权威口径），单位核。一个配对 = 同一时间窗内紧邻的 A、B 各一次。
- **中心值** = 同基线同档位全部有效运行的**中位数**（n=3；RTMP 的 A 臂 n=2）。
- **Δ_center** = median(B) − median(A)：先聚合再求差。
- **Δ_pair** = median over 配对 i of (B_i − A_i)：先逐对求差再取中位。两者不等价，必须同时给出。
- **相对值**：报告里每一个百分比都必须写明分子。`Δ_center / median(A)` 与 `Δ_pair / median(A)` 可以符号相反；另有“配对内相对值” `(B_i−A_i)/A_i` 再取中位，用于避免单个高负载配对主导绝对差。
- **波动**：同臂重复的极差（max−min）与平均绝对偏差（MAD）。
- **判定**：用配对差的 t 区间（n=3 时 df=2，t=4.303）判断是否存在差异，再与工程阈值（2%）比较，分为①差值未超过噪声（区间覆盖 0）、②超过噪声但不足以证明生产代码变化、③有统计支持的系统性差异。

> 本节取代本文初版使用的“|配对差中位| > max(臂内 max−中位) 且符号一致”规则。该规则是单侧偏离量，不是检验，且与表中中心值不同源，已导致两处过度判定（见 §5.2）。

脚本与原始数据：TEST 侧 `/var/tmp/media_server_perf/20261013T011210Z-7788320/` 下的 `pi_phase6.py`（执行器）、`pi_phase6a.py`（分析器）、`plan6a.jsonl`/`plan6c.jsonl`（调度）、`phase6b/`、`phase6c/`（逐例 `result.json` 与 `summary.jsonl`）。

### 5.2 对初版结论的修正

1. **相对百分比与中心值不同源**。初版表格的“相对”列是 `Δ_pair / median(A)`，而同一行的 A/B 中心值是中位数。两者可以符号相反，HTTP-FLV 就是实例：
   - 配对 1：A=1.9582 B=1.9806 → **d=+0.0225（+1.15%）**
   - 配对 2：A=1.9807 B=1.9710 → d=-0.0096（-0.49%）
   - 配对 3：A=1.9672 B=1.9589 → d=-0.0083（-0.42%）

   中位数把 A 臂取到 1.9672、B 臂取到 1.9710（Δ_center=+0.20%），而配对差中位取到 -0.0083（-0.42%）。**不是数据错误，是估计量不一致造成的表述错误**：同一行混用了两种口径。修正方式是两个估计量都列出，并以其一并存的不确定性作结论（此处两者都被同臂极差 0.0225 淹没）。
2. **“噪声门限”定义不成立**。初版用的是 `max(臂内 max − 臂内 median)`（单侧偏离），既不是检验也不是双侧区间。按配对差的 t 区间重算后，**初版标为“略超门限”的 whep-s8-1200（-0.9%）与 gb-tcpa-1000（-0.2%）均不成立**，应撤回；whep-s1-1200 虽然 |Δ_pair|=0.0328 大于当时写的 0.0260，但三个配对里有一个方向相反（+0.0022），同样不构成差异。
3. **不能因为数值小就声称低于噪声**。正确依据是：配对差区间覆盖 0（六个档位均是），且同臂极差（0.0127~0.0634 核）大于或接近全部观测差。反过来，即使某档区间不覆盖 0，在客户端 ELF 同时改变的前提下也只能归为②，需要交叉替换才能归因。
4. 其余指标（每核 busy/system/softirq、客户端 CPU、PSS）的初版判定同样基于已作废的门限规则，应理解为“幅度均 ≤ 2.2% 且未通过任何检验”，不再单独标注“真实差异”；`phase6_calibration_raw_table.txt` 的“判定”列同属初版规则，保留作过程记录。user/system 拆分出现方向相反的内部变化（flv-800：user +2.6%、system -1.4%，合计 -0.4%），PSS 在两档上方向相反（-1.5% / +2.1%），均无系统性方向。
5. **系统 softirq 负载在 A/B 之间没有系统性差别**（每核 softirq 差均在同臂波动内），即观测差既不能由环境解释，也不需要由环境解释。

**RTMP 档位的敏感性检查**（不变）：该档 3 个 A 运行中有 3 次因客户端测量结束时间戳竞态被判 `UNCONFIRMED`（见 §9）。严格只取 `HEALTHY` 时 A 中心 1.6479、Δ_center=+0.0004；把含竞态的运行一并计入时 A 中心 1.6470、差 +0.0013。两者都 < 0.1%，且区间都覆盖 0，结论不变。

按固定另一侧计算净效应：

| 效应 | 客户端固定在 A | 客户端固定在 B |
| --- | ---: | ---: |
| 服务端换版本 | -0.47% | -0.22% |
| 客户端换版本 | -0.41% | -0.16% |

两个方向的服务端效应与客户端效应**互相穿插、量级相同**（0.16% ~ 0.47%），且混合组合各只有 2 次，无法分离归因。能可靠说的是：

- 总差异（-0.63% ~ -0.84%）中，客户端代码变化可以解释其中相当一部分，**不能把它当作服务端改进**；
- 无论服务端还是客户端，单侧效应都不超过 0.5%，低于本方法在同臂重复上的分辨率（A 臂自身极差就有 0.0557 核 = 1.2%）；
- 因此 §5 的①类判定不会因为客户端混淆而改变：本方法无法分辨 1% 以内的任何变化，无论它来自哪一侧。

## 8. 阶段 6 正式 profiling 计划（待批准后执行）

**目标**（按既定优先级）

- P1 WHEP 的每源固定成本（阶段 4B 拟合 50.8 mCPU/源，与观看数无关）来自哪里；1200 观看时 CPU 曲线趋平的机制是什么。
- P2 GB UDP 与 GB TCP 的成本差异机制（本标定：2.48 核 vs 1.91 核，内核占比 75.8% vs 55.2%）。
- P3（次要）FLV 与 RTMP 的 0.32 核差值。

**采样点**（每点 30 s `perf record`，与容量测量分离运行，profile 数据不作为容量结论）

| 编号 | 负载 | 目的 |
| --- | --- | --- |
| W0 | WHEP S=1 V=0（仅推流） | 扣除公共基线 |
| W1 | WHEP S=8 V=0 | 与 W0 差分 → 每源固定成本画像 |
| W2 | WHEP S=1 V=200 | 线性区画像 |
| W3 | WHEP S=1 V=1200 | 与 W2 差分 → 趋平区新增成本 |
| G1 / G2 | GB UDP V=1000 / GB TCP V=1000 | 互差 → UDP/TCP 路径归属 |
| F1 / R1 | FLV V=800 / RTMP V=800 | 次要目标 |

**方法**

1. `perf record -F 199 -g --call-graph dwarf,16384`，**不加 `-U`**：GB UDP 76% 在内核，必须保留内核栈；用户/内核归属由 `perf report --sort=dso,symbol` 区分。
2. 同窗口并行 `perf stat`：`context-switches`、`cpu-migrations`、`page-faults`、`instructions`、`cycles`（IPC），用于判断是计算密集还是调度/缺页密集。
3. 差分优先于单点：`perf diff` 比较 W1-W0、W3-W2、G1-G2，避免把"到处都有的收发包开销"当成协议特有成本。
4. syscall 面：`perf trace -p <pid>`（或 10 s `strace -c -f`）统计每秒调用次数与类型，验证 §7 推断（UDP 每包一次 `recvmsg`/`sendmsg`，WHEP 是否有批量调用）。
5. softirq 归因沿用本标定的每 CPU × 类型窗口采样，与 profile 时间对齐。
6. 每个采样点重复 2 次，两次热点排序不一致时不给出结论。
