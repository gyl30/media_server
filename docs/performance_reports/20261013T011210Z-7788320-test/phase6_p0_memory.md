# P0-M：WHEP 内存稳定性与清理后回落

基线 `7788320af210ab63939c84b6fdcb4e7518674caa`，TEST `<TEST_HOST>`，运行目录
`/var/tmp/media_server_perf/20261013T011210Z-7788320/phase6m-*`。
本轮不修改生产、测试与 third 代码，不改全局系统设置。

## 1. 结论（先给判定）

按 §2 的 A/B/C 三类分别判定：

| 类别 | 判定 | 一句话结论 |
|---|---|---|
| **A 建立期一次性分配** | **存在，且与观看数严格线性** | 0.249 MiB/观看（V1200 实测回归），与阶段 6 自管模式的 0.263 MiB/观看一致 |
| **B 固定负载期间持续增长** | **不存在** | 900 s 稳态 PSS 斜率 −0.009 MiB/s（等于 0），RSS 斜率同样为 0；周期 12 s 的锯齿每周期完全回落 |
| **C 清理后不回落** | **存在，但性质是分配器保留，不是泄漏** | V1200 关闭全部 viewer 后 PSS 停在 302.8 MiB（基线 19.8）且 300 s 平坦；但 jemalloc 自报 **allocated 仅 7.5 MiB**（V1500 为 8.4 MiB）；第二轮同规模观看端不再叠加，新分配活动触发后 5 s 内归还 ≥222 MiB |

**对容量规划的含义**：`pss_kib_max`（峰值）是正确的使用维度；teardown 后的 PSS 会高估活跃用量约 285 MiB，
因为它包含分配器保留页。原因见 §6：本进程的 jemalloc 以 `background_thread: false` 运行，
页衰减只在有分配活动时推进，因此空闲时 PSS 不会自行下降，但会在下一波连接时立即归还。
阶段 6 报告 §7 的"每观看端 0.26 MiB 建立期分配"仍然成立，
本轮补充的是"这部分内存在 viewer 关闭后不会立即归还内核，但会被后续连接复用"。

## 2. 方法与判定标准

### 2.1 三类增长性质的定义

- **A 建立期一次性**：PSS 增量与连接数成正比，且只在建连窗口内出现。
- **B 稳态持续增长（泄漏型）**：连接数恒定时 PSS 随时间单调上升。
- **C 清理后不回落**：全部连接关闭并等待远大于分配衰减时间后，PSS 仍高于建立前基线。
  进一步区分"活跃对象"与"分配器保留"：若第二批同规模连接**复用**了这部分内存（总水位不叠加），
  则为分配器保留；若逐轮叠加，则为泄漏。

### 2.2 让 DUT 跨 viewer 关闭而存活

`perf_run` 的 `existing` 模式明确不停止外部服务，因此由本测试自己拥有 signaling 与 media_server，
播放用 `--input existing --server-pid <pid>`。这样"关闭全部 viewer"与"继续观察同一进程"
可以在不改任何测试代码的前提下同时成立。

编排（`pi_phase6mem2.py`，仅测试侧脚本）：

```
signaling(真实 Go) → media_server(持久) → 采样器 → 空闲 60s → 发布 1 路 RTMP → 单源 60s
  → 周期1：whep:N 稳态 900s → 关闭全部 viewer 观察 300s
  → 周期2（仅 V1200）：再次 whep:N 稳态 300s → 关闭观察 300s
  → 停止发布者 60s → 结束
```

### 2.3 采样与阶段划分

- 采样器 `pi_phase6samp.py` 独立进程，**5 s 间隔逐行落盘**，字段含 PSS/RSS/VmHWM/VmSize/线程/FD/
  socket/UDP 队列与掉包/TCP 重传/进程用户-内核 jiffies/每核忙度。
- **阶段边界来自被测系统本身**：用 DUT 的 FD 数（每个 WHEP 观看端对应一个连接）划分
  空载/建连/稳态/清理，不依赖驱动脚本的时钟。
- 每轮播放由 `perf_run` 自己判定媒体健康（ready/progressing/failed、覆盖率），不用日志 grep 代替。

### 2.4 环境前置（本轮踩到的坑）

DUT 的 FD 软上限默认 1024 时，约 700 个 WHEP 观看端就会耗尽，表现为后两组永远不 ready、
最终 `all-viewer readiness timed out`。这与服务无关，是测试进程的资源上限。
本轮按阶段 5 已批准的做法，在外层包装脚本里对**本测试自己的进程**设置 `ulimit -n 65536`
（不改全局），并在驱动里断言 `/proc/<dut>/limits` 为 65536 后才继续。

## 3. 结果：V1200 双周期

两轮播放均 PASS（覆盖率 0.9999998 / 0.9999996，`failed` 为空），驱动 `status=PASS`。

### 3.1 基线水位

| 阶段 | PSS | FD | 线程 | VmSize |
|---|---|---|---|---|
| 进程刚启动 | 15.6 MiB | 26 | 8 | 195 MiB |
| 1 路 RTMP 源，无观看端 | **19.8 MiB** | 33 | 16 | 239 MiB |

单源 19.8 MiB 与阶段 3.2 独立测得的 19.9 MiB 一致，说明 `existing` 模式与自管模式的 DUT 状态可比。

### 3.2 A：建立期一次性分配

| 周期 | 连接数 | PSS 变化 | 每观看端（回归斜率） |
|---|---|---|---|
| 1 | 0 → 1201 | 43.6 → 317.0 MiB | **0.249 MiB** |
| 2 | 0 → 1201 | 114.0 → 347.1 MiB | 见 §3.4（复用已保留内存） |

0.249 MiB/观看与阶段 6 自管模式 V1200/V1500/V1800 的 0.263/0.287/0.264 MiB 同量级，
**[实测] 两个独立测量路径互相印证**。

### 3.3 B：稳态无增长

| 指标 | 周期 1（稳态 900 s，取后半 460 s） | 周期 2（稳态 300 s，取后半 160 s） |
|---|---|---|
| PSS 均值 | 318.1 MiB | 347.0 MiB |
| PSS 线性斜率 | **−0.009 MiB/s** | **−0.006 MiB/s** |
| RSS 线性斜率 | −0.010 MiB/s | −0.006 MiB/s |
| 线程 | 16（恒定） | 16（恒定） |
| UDP 掉包 | 0 | 0 |
| TCP 重传 | 0.00/s | 0.00/s |

**[实测] 两个周期的稳态都没有任何单调增长。** 观测到的波动是周期 12 s 的锯齿
（阶段 6 的 1 s 采样已确定其周期与 fixture 循环长度 12.0 s 相同），幅度约 26-30 MiB，
每周期完全回落。本轮 5 s 采样对 12 s 周期存在混叠，脚本报告的"周期 25 s"是采样伪影，不是真实周期。

### 3.4 C：清理后不回落，但可被复用

周期 1 关闭全部 viewer 后（t=0 为最后一个连接关闭）：

| t | PSS | RSS | VmSize | FD | 线程 | 进程 CPU |
|---|---|---|---|---|---|---|
| −5 s | 317.0 | 323.6 | 2581 | 1233 | 16 | 21.4% |
| +5 s | 303.6 | 306.8 | 2581 | **33** | 16 | 0.26% |
| +30 s…+300 s | **302.8（完全平坦）** | 306.0 | 2581 | 33 | 16 | ~0.2% |
| 周期 2 建连时 | 114.0（5 s 内） | 119.1 | 2581 | 178 | 16 | — |

- **FD 精确回到基线**（1233 → 33，基线 32），线程数不变（8 worker + 摄入线程，本就不随观看端变化）。
- 内存只回落 14 MiB，此后 300 s 内没有任何进一步下降趋势。
- 关闭后 +120 s 直接读 `/proc/<dut>/smaps_rollup`：
  `Pss 307582 kB / Anonymous 287268 kB / LazyFree 0 kB`。
  **[实测] 残留不是 `MADV_FREE` 惰性页**，而是实际驻留的脏匿名页。

判定"活跃对象 vs 分配器保留"的两个独立证据：

1. **第二轮不叠加**：周期 2 再次建立 1200 个观看端，峰值 369.5 MiB、清理后 308.4 MiB，
   与周期 1 的 302.8 MiB 相差 +5.6 MiB（1.8%）。若这 283 MiB 是上一批 viewer 的活跃对象，
   第二批必然再要约 300 MiB；实测没有。
2. **新分配活动触发归还**：周期 2 开始建连的那 5 s 内，PSS 从 300.4 直接降到 114.0
   （同一行样本 FD 已从 33 涨到 178），即分配器在需要分配时把 ≥222 MiB 归还了内核，
   随后新连接再按需取用。

**[实测 + 推断] 结论：C 类残留是 jemalloc 的保留页（分配器持有、按衰减策略延迟归还内核），
不是每连接的活跃对象泄漏。** 直接读取 jemalloc 自身计数见 §6（已实测，allocated 7.5 MiB）。

### 3.5 峰值、停止源后的行为与安全预算

- 整轮 PSS 峰值 **369.5 MiB**（周期 2 建连阶段），远低于 `max-server-pss-mib 16384`；
  主机可用内存全程 >39 GiB，未触发任何预算，`server.log` 无 warning/error。
- 两轮播放均 **PASS**：1200 观看端全部 ready/progressing，`failed` 为空，
  覆盖率分别 0.9999998 与 0.9999996；驱动 `status=PASS`，自有进程全部回收。
- **最后一步的旁证**：停止发布者（本进程最后一次批量分配/释放）后，PSS 从 336.5 进一步降到
  **241.2 MiB**（仍高于 19.8 基线）。又一次“只在有分配活动时归还”，与 §6 的
  `background_thread: false` 一致。最终水位仍不是活跃量（allocated 7.5 MiB）。

## 4. 结果：V1500 单周期

播放 PASS（1500 观看端全部 ready/progressing，`failed` 为空，覆盖率 0.9999998），驱动 `status=PASS`。

| 阶段 | 结果 |
|---|---|
| 基线（1 路源，无观看端） | 19.8 MiB（与 V1200 完全一致） |
| A 建立期 | **0.262 MiB/观看**（回归，样本 201），PSS 43.6 → 415.4 MiB，峰值 474.2 MiB |
| B 稳态 900 s（取后半 465 s） | PSS 均值 411.2 MiB，斜率 **−0.022 MiB/s**，RSS 斜率同样为负；线程 16 恒定；UDP 掉包 0；TCP 重传 0 |
| C 清理后 | 415.4 → 379.1（+30s）→ 346.2（+60s）→ 309.6（+120s）→ **242.9（+300s）**，回落 41% |
| 停止发布者后 | 244.4 MiB（末值），FD 回到基线 32，线程 16，VmSize 3029 MiB |

与 V1200 的关键差异：**V1500 的清理后 PSS 是持续下降的，而 V1200 周期 1 完全平坦。**
两边最后都收敛到几乎相同的水平（V1200 末值 241.2 MiB，V1500 末值 244.4 MiB），
而两者的峰值（352 / 415 MiB）与观看数（1200 / 1500）都不同。

**[实测 + 推断] 这与 §6 的机制一致：jemalloc 的页衰减需要分配活动驱动，**
衰减工作量与脏页量相关（V1500 脏页更多，因此每个衰减 tick 能推进更多），
而最后保留的水平与观看数无关（两者都约 242 MiB）——**它不是每观看端的活跃对象**。

### 4.1 V1500 的分配器直接计数（第二个数据点）

清理后（FD 已回基线 33，PSS 249.6 MiB）用 gdb 调用 `malloc_stats_print`：

```
Pss: 249645 kB  Anonymous: 228424 kB  LazyFree: 0 kB
Allocated: 8779824, active: 25837568, metadata: 13006192 (n_thp 0),
resident: 1269358592, mapped: 1300873216, retained: 1620459520
```

**[实测] 1500 个 viewer 全部关闭后，活跃对象只有 8.4 MiB**（V1200 为 7.5 MiB），
而内核驻留 249.6 MiB、`LazyFree` 仍为 0。完整输出已归档 `jemalloc-v1500-after-teardown.txt`。

## 5. 与既有结论的关系

- 修正并补强阶段 6 报告 §7：那里给出"建立期 0.26-0.29 MiB/观看、窗口内无单调增长"，
  本轮在同基线上用完全独立的 `existing` 模式路径复现，并补上了"清理后"这一维度。
- 对阶段 5 容量表的 PSS 列无影响：容量判定用的是 `pss_kib_max`（峰值），本来就是正确的维度。
- 新增一条运维含义：**churn 之后的 PSS 不能当作活跃用量**，会高估约 0.24 MiB/历史峰值观看端。

## 6. 分配器直接计数（已实测）

DUT 无信号处理（`main.cpp` 只调用 `service::run()`），`MALLOC_CONF=stats_print:true` 需要正常退出才会输出，
而 SIGTERM 不触发 atexit。因此改用运行时调用：在周期 2 清理后（PSS 315.7 MiB、FD 已回基线）
用 `gdb -p <dut> -batch -ex 'call (void)malloc_stats_print(0,0,0)'` 让分配器把统计写到自己的 stderr（即 DUT 日志）。
完整输出已归档：`jemalloc-after-teardown.txt`。

**[实测] 关闭全部 1200 个 viewer 后，jemalloc 自报：**

```
Allocated: 7868592, active: 23556096, metadata: 12446576 (n_thp 0),
resident: 1666801664, mapped: 1698873344, retained: 752697344
Version: "5.3.0-0-g54eaed1d..."    opt.narenas: 32
opt.background_thread: false        opt.dirty_decay_ms: 10000
```

| 量 | 值 | 含义 |
|---|---|---|
| **allocated** | **7.5 MiB** | 活跃对象（此时仍在发布 1 路源） |
| active regions | 22.5 MiB | 包含内部碎片的在用页 |
| 内核驻留（PSS） | 315.7 MiB | 实际占用的物理内存 |
| mapped | 1620 MiB | 地址空间（已含被 madvise 的页） |
| retained | 718 MiB | 已归还内核的部分 |

**[实测] 活跃对象只有 7.5 MiB，而内核驻留 315.7 MiB——差的约 285 MiB 不是泄漏，是分配器持有的未衰减脏页。**

机制也由同一份输出直接解释：`opt.background_thread: false`。jemalloc 的页衰减（`dirty_decay_ms` 虽为 10 s）
**只在有分配活动时被推进**；空闲时没有分配调用，因此不会自行归还——这与 §3.4 的两个行为观察完全对应：
清理后 300 s 平坦不降，而周期 2 一开始建连，5 s 内就归还了 ≥222 MiB。

这是一条运维含义（**不是本次要改的选项**）：若希望 PSS 跟随活跃度，需要 `background_thread:true`
或类似的分配器配置；但容量判定本来就应该用峰值，因此不需要为此改配置。

两个档位都做了同样的直接测量（V1500 见 §4.1）：allocated 分别为 7.5 与 8.4 MiB，
与内核驻留 315.7 / 249.6 MiB 相比都是两个数量级以下。

## 7. 限制

1. 采样间隔 5 s，无法解析 12 s 锯齿的相位与真实幅度（阶段 6 的 1 s 采样已覆盖该维度）。
2. 未做 heap profile（TEST 缺 `jeprof`）；但分配器自身的 allocated/retained 已直接测得（§6），
   C 类性质不依赖推断。
3. 观察窗口 300 s。jemalloc 默认 `dirty_decay_ms=10000`，300 s 已远大于衰减时间，
   因此"300 s 内不回落"不是衰减窗口未到；但更长期（小时级）的自发归还未观察。
4. 只覆盖 WHEP。GB/FLV/RTMP 的清理行为未测（P1/P2 只做 CPU 归因）。
