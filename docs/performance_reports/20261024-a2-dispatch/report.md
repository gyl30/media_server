# A2 跨 worker 分发公平性优化与 A/B 验证

## 结论

**判定：ACCEPT，采用 B3 20 ms 时间片。**

- **根因已确认。** F4 的主要原因是跨 worker 的 `sink_group::drain()` 在接近饱和时独占事件循环：它排空才返回，GB UDP 与 WHEP 的同步交付使单次执行达 1～2 s，窗口后批量删除时达 37.9 s。同一 worker 上的 HTTP 控制请求、WHEP 的 POST、STUN 与 DTLS 都要等它返回（第 2 节）。
- **修改。** drain 仍连续交付积压帧，但每交付一帧检查一次耗时，超过 20 ms 就在帧边界重新投递自己。生产 diff 为 +23/−15 行，没有新增运行时状态、锁、配置或线程。
- **F4 的消除可重复。**
  - WHEP 3500：A 3 轮通过 1 轮，B 3/3 通过；窗口内服务端的 ICE 活动超时从 9/23/96 个降到 0。
  - GB UDP 8000：A 3 轮通过 1 轮，B 3/3 通过；窗口后删除从 256/8000、19/8000 变为全部完成。
  - 在上一轮的稳定容量点 WHEP 3250 和 GB UDP 7500，控制探测 p99 从 963、1669 ms 降到 178、331 ms。GB sender create/delete p99 从 1039/1986 ms 降到 349/778 ms，WHEP 的 lag span p50 从 894 ms 降到 402 ms。
- **没有用媒体吞吐换控制响应。** 15 个负载点的媒体 Gbit/s 相同，每 viewer 周期差异在 ±1.6% 以内。环境哨兵为 2.60 vs 2.61 Mcycles/viewer，UDP 丢包为 0，没有新增 RTP 序号或时间戳错误。
- **代价在 GB TCP 的过载区。** CPU 拐点（9500～10000）之后，GB TCP active 12000～13000 的爬坡 create p99 平均增加约 2.5 s。13000 时，B 有 1/6 轮因 create 超过 10 s 失败（A 0/6）；两版另各有 1/6 轮因实时比例低于 0.98 失败。原因是时间片限制了过载时的写合并（3.4、第 9 节）。5 ms 时间片会把这一回归扩大到 12000 全部失败，因此被否决。
- 已在本地提交，未 push。

## 2 F4 的根因与证据

### 2.1 现象复现（A）

诊断轮次带 bpftrace uprobe（`tools/drain.bt`，挂在三种 `sink_group::drain()` 与 `snapshot_sinks()` 上），并每 0.5 s 用 curl 对服务端 HTTP 端口发一次新连接请求。这些轮次只用于定位，不进入 A/B 统计（`raw/diag/`、`raw/runs/a2d-*`、`raw/runs/v-*`）。

| 负载（A） | 媒体面 | 单次 drain 最长 | 单批最长 | ≥0.5 s 的 drain | curl p50 / p90 / p99 / 最长 |
| --- | --- | --- | --- | --- | --- |
| GB UDP 7000 `a2d-gb_udp-7000-A` | PASS | 1.28 s | 217 ms | 57 次 | 24 ms / 0.63 s / 1.37 s / 1.52 s |
| GB UDP 8000 `a2d-gb_udp-8000-A` | 实时，清理失败 | 1.90 s（测量窗口内） | — | 62 次 | 77 ms / 1.70 s / 5.6 s / 20 s 超时 |
| GB UDP 8000 `v-gb_udp-8000-A` | 实时，清理失败 | **37.9 s**（窗口后批量删除时） | 564 ms | 197 次 | 30 ms / 1.25 s / 2.03 s / 20 s 超时 |
| WHEP 3500 `v-whep-3500-A` | PASS | 2.31 s | 254 ms | 400 次 | 84 ms / 0.90 s / 1.39 s / 1.49 s |
| RTMP 8500 `a2d-rtmp-8500-A` | PASS | 78 ms | 58 ms | 0 | 41 ms / 61 ms / 125 ms / 151 ms |

- GB UDP 8000：窗口结束后，32 个客户端组各自顺序删除 256 个 sender。每组只删掉 0～1 个，就因 10 s 请求超时而停止（`phase=cleanup created=256 deleted=0/1`），与上一轮的 F4 一致。
- WHEP 3750（`a2d-whep-3750-A`）：每个客户端组串行建立 256 个会话。前几组 8～9 s 建完；从第 2816 个会话起每组要 53～55 s，约每个会话 210 ms。有一个会话 `STUN nomination timeout`（客户端单次 STUN 等待 2 s）。第 3328 个会话所在的组在 240 s 就绪时限内没有建完。
- GB UDP 7000 时，7 个目标 worker 的 PS drain 在 40 s 内累计执行 29.8～31.3 s，占 74%～78%。

### 2.2 机制

A 的 `sink_group::drain()`（`media/core/worker_sink_dispatcher.h:183-221`）在一个 handler 内执行 `for (;;)` 循环：每轮 swap 出全部待交付帧，交付后再取，直到 pending 为空才返回。

- **GB UDP 与 WHEP 的交付是同步的。** `gb28181_rtp_sender::on_ps_frame()` 在 drain 内完成 RTP 打包，并经 `udp_transport` 直接非阻塞发送；`whep_session::on_frame()` 在 drain 内完成 RTP 打包、SRTP 加密和发送。一个关键帧约 64 个 RTP 包，交付给同一 worker 上约 1000 个 sender，就是 6～7 万次 `sendmsg`，单批耗时 130～560 ms。
- **接近饱和时循环不返回。** worker 74%～88% 的时间在交付媒体，每批交付期间又有新帧到达（单源 720p30 + AAC，约每 13 ms 一帧），pending 几乎不会变空，循环把一个 GOP 内的多个批次连成 1～2 s。窗口结束后 32 组同时删除 sender，额外负载让单次 drain 持续了 37.9 s。
- **被阻塞的是同一 io_context 的全部其他 handler。** HTTP 连接按轮转分给各 worker（`service.cpp:44-69`），以下操作都要等 drain 让出：控制请求的读取与应答，WHEP 的 POST、STUN 应答和 DTLS 握手，各监听端口的 accept 协程（每个监听器固定在一个 worker 上）。
- **RTMP/RTSP/HTTP-FLV 不受此影响。** 它们的 sink 只复制数据并 `post` 写操作（`tcp_transport::write()`），每批 drain 只需几十毫秒，RTMP 8500 时最长 78 ms。这些协议在饱和点的失败形态是 F5，不是 F4。

### 2.3 判定

F4 的主要原因，是跨 worker drain 在接近饱和时长时间独占事件循环。证据是：CPU、媒体负载和吞吐都不变，只让 drain 交还执行权，控制面延迟就下降一个数量级（第 3、6 节）。剩余的尾部延迟来自单个关键帧同步交付给整组 sink 的耗时，单帧粒度下最长 219～362 ms（第 7、11 节）。

## 3 原始实现的问题与修改

### 3.1 原实现

```text
publish (source worker)            target worker io_context
  pending.push_back(frame)   ──►   drain(): for (;;) {
  if (!drain_queued) post(drain)          swap(pending) → batch
                                          deliver batch to all sinks
                                          pending 为空才 return
                                        }
```

`drain_queued` 保证每组只有一个 drain 在途，帧序与 end 顺序正确。问题只在于“排空才返回”：一个 handler 的执行时间随负载无界增长。

### 3.2 候选

所有候选都只改 `drain()`，都保留 `drain_queued` 单 drain 不变量以及 overflow/end 路径：

| 候选 | 让出条件 | 结果 |

| B1 | 每处理完一次 swap 出的批次 | 否决：饱和时一批仍含关键帧后的积压，WHEP 控制延迟比 A 更差 |
| B2 | 每交付完一帧 | 否决：控制面最好，但 GB TCP passive 每 viewer 周期 +16%（3.3） |
| B3 5 ms | 连续交付，单次执行超过 5 ms 后在帧边界让出 | 否决：GB TCP active/passive 12000 全部失败，A 全部通过（3.4） |

### 3.3 B2 为什么被否决

第一轮完整 A/B（A 对 B2，数据见附录）证明，B2 在 WHEP 和 GB UDP 上解决了 F4，且 CPU 基本不变。但是中等负载下按协议核对成本时，发现了 B2 的回归：

| 负载 | Mcycles/viewer A → B2 | 指令/viewer | 服务端核 |
| --- | --- | --- | --- |
| GB TCP passive 7000 | 2.37 → 2.75（**+16%**） | +27% | 6.10 → 7.07 |
| 混合 7000 | 2.87 → 2.96（+3.1%） | +3% | 7.43 → 7.69 |
| RTSP 6000 | 2.75 → 2.82（+2.5%） | +3% | 6.10 → 6.25 |
| HTTP-FLV 6000 | 2.56 → 2.61（+2%） | | |
| WHEP 3250 / 3500 | +1.4% / +1.6% | +0.3%～+1% | |
| GB UDP 7500 / 8000、RTMP 8500 | 0% | 0% | |

原因是 B2 破坏了 sink 端的写合并：

- `gb28181_tcp_sender_session::send_packet()`（`media/gb28181/gb28181_tcp_sender_session.cpp:117-138`）把每个 RTP 包追加到 `output_`。只有 `output_` 原本为空时，它才 `post` 一个 flush，由 flush 把整个 `output_` 一次写给 transport。
- A 的一个 drain 连续交付多帧时，这些帧都在 flush 运行前追加进 `output_`，合并成一次写。B2 每帧后重新投递 drain，排在它前面的 flush 先执行，于是每帧各写一次，写次数、transport 队列操作和系统调用随之增加，指令数 +27%。
- 混合负载的另一部分额外成本来自 TCP 报文段数。剖析显示每 viewer 每秒的 TCP 数据段从 47.0 增加到 51.7（+10%），`sendto` 次数只多 1.5%（`raw/prof/mix7000-*`）。服务端 TCP socket 没有设置 `TCP_NODELAY`。在 A 中，WHEP/GB 的长 drain 会让同一 worker 上 TCP 连接的写积压后集中发出，回环上的 Nagle 把部分写合并成一个段；B2 按帧的节奏发出，合并减少。回环上服务端 CPU 还要承担接收端的协议栈处理，这项成本在测试环境中被放大。

新增的分发器测试场景 `deferred_flush_coalesces`（4.2）模拟这种“首次追加时投递 flush”的 sink：A 和 B3 下 10 个积压帧合并为 1 次 flush，B2 下变成 10 次。

### 3.4 时间片的选择

B3 在 A 的连续交付循环上加了一个让出条件：每交付完一帧检查一次耗时，超过时间片就重新投递自己并返回。

- 中等负载下，一次 drain 通常在时间片内处理完全部积压帧，行为与 A 相同，sink 的写合并得以保留。
- 接近饱和时，handler 的执行时间被限制在“时间片 + 一帧的交付时间”。最坏情况是一个关键帧交付给约 1000 个 sink，与 B2 的下限相同。

- **A 在过载时靠长 drain 合并写。** GB TCP active 的每 viewer 周期从 10000 时的 2.14 降到 12000 时的 1.80、13000 时的 1.66 Mcycles，服务端始终在 7.9 核左右，媒体保持实时，lag span 从 363 ms 增加到 578 ms。原因与 3.3 相同：drain 连续交付多帧时，sink 的 `output_` 在 flush 运行前积累了更多帧，一次写出。这正是上一轮报告记录的“拐点之后每 viewer 成本下降”。
- **5 ms 时间片限制了这种合并。** 11000 时两版成本相同（1.96 vs 1.97），12000 时 5 ms 两轮都在爬坡末段失败，passive 12000 也失败：最后一组的 `/gb28181/sender/create` 全部超过客户端 10 s 时限，客户端放弃并关闭监听后，服务端的连接被拒（`Connection refused`）。
- **这不是 F4 的 drain 独占。** 同一负载的诊断（`raw/diag/v-gb_tcp_active-12000-*`）中，单次 drain 最长为 82 ms（A）、70 ms（5 ms）和 59 ms（20 ms）。带 bpftrace 与 curl 探测的额外开销时，A 通过，5 ms 和 20 ms 都在爬坡末段因 create 超时失败。在爬坡末段 CPU 过载期间，A 的 HTTP 探测最长 3.6 s，5 ms 有约 20 s 只收到 3 次应答，最长 6.8 s。5 ms 每次只合并 5 ms 内的帧，需求超过 8 核后就绪队列持续积压；A 合并得更多，需求与处理能力能重新平衡。
- **20 ms 基本保住了过载容量。** 这一轮补测中，active 12000（2/2）、13000（2/2）和 passive 12000 都通过，每 viewer 周期与 A 相同（1.80/1.66 Mcycles）。但爬坡 create p99 和 13000 的 lag span 仍高于 A，说明合并受限的效应在 20 ms 下变弱，但没有消失。正式 A/B 加测到 13000 各 6 轮、13750 各 4 轮，结果见第 8、9 节。

因此采用 20 ms，并对它重做完整 A/B（第 6～8 节）。5 ms 的完整 A/B 数据保留在附录 A。

### 3.5 B3 的代码

```cpp
static constexpr auto drain_time_slice = std::chrono::milliseconds{20};

void drain()
{
    const auto deadline = std::chrono::steady_clock::now() + drain_time_slice;
    for (;;)
    {
        std::optional<Frame> frame;
        {
            std::scoped_lock lock(mutex);
            if (!pending.empty())   { frame = std::move(pending.front()); pending.pop_front(); }
            else if (pending_end)   { pending_end = false; drain_queued = false; }
            else                    { drain_queued = false; return; }
        }
        const auto sinks_snapshot = snapshot_sinks();
        if (!frame) { for (sink : sinks_snapshot) sink->on_end(); return; }
        for (sink : sinks_snapshot) deliver(*frame);
        if (std::chrono::steady_clock::now() >= deadline)
        {
            post(worker.io(), [self = shared_from_this()] { self->drain(); });
            return;
        }
    }
}
```

`sink_group` 继承 `std::enable_shared_from_this`，重新投递的 handler 持有组的 `shared_ptr`，与原来 `publish`/`end` 投递 drain 时相同。新增内容只有一个编译期常量和每帧一次的 `steady_clock::now()` 比较，没有新增运行时状态、锁、配置或线程。生产 diff 为 `media/core/worker_sink_dispatcher.h` +23/−15；`docs/media-lifecycle.md` 同步更新了描述。

### 3.6 语义变化（只在过载时可见）

- A 中已经 swap 进当前批次的帧不计入 2500 帧上限，过载时一个组实际能积压到上限的近两倍才被结束。B3 每次只从 pending 取一帧，未交付的帧都留在 pending 中，上限按真实积压计算，过载组会更早被结束。`docs/media-lifecycle.md` 原本就描述为“待交付帧达到 2500 帧上限”。
- sink snapshot 改为每帧取一次，remove 的生效粒度从“一批”变为“一帧”，仍符合“remove 不撤销已取得的 snapshot”。

## 4 生命周期与并发正确性

### 4.1 可达时序分析

| 项目 | 原实现保证 | B3 |
| --- | --- | --- |
| 同源帧序 | `drain_queued` 保证每组只有一个 drain 已投递或在执行，pending 为 FIFO | 不变：重新投递期间 `drain_queued` 保持为真，`publish` 不会再投递第二个 drain |
| end 与已排队帧 | `end()` 之后 `publish` 跳过该组；drain 在 pending 为空且 `pending_end` 时才交付 end | 不变：只有 pending 为空才走 end 分支；end 的 snapshot 在 end 分支内获取，`end()` 前加入的 sink 也能收到 |
| 溢出与慢消费者 | 第 2501 帧到来时清空 pending、置 `pending_end`、从 map 摘除该组 | 路径不变；下一次 drain 看到空队列与 `pending_end`，交付 end。上限按真实积压计算（3.6） |
| add / remove / 失效 | sink 以 `weak_ptr` 保存，snapshot 在每批开始时获取 | snapshot 每帧获取；remove 或 sink 析构最晚在下一帧生效 |
| 任务丢失、重复调度、永久积压 | 循环到空为止 | 超时让出时 `drain_queued` 仍为真并重新投递，下一次 drain 继续；发现为空时才清 `drain_queued`，不会丢失或重复。worker 停止时 `request_stop` 只释放 work guard，已投递的 drain 会继续执行到队列为空 |
| 生命周期 | 投递的 handler 持有组的 `shared_ptr` | 重新投递同样持有 `shared_ptr`，组在最后一个 drain 结束后释放 |
| 同 worker 与跨 worker | 同 worker 在 `publish` 内直接调用 sink | 同 worker 路径未改；每次读取输入只交付一帧，本来就有界 |
| 关键帧起播 | 由各 sink 自行等待自然关键帧（D02） | 分发器不参与，未改 |

## 5 A/B 方法

- 环境与上一轮相同（`../20261023-891aec1-8core/report.md` 第 2 节）：Xeon Silver 4216；媒体服务 `--threads 8` 绑定物理核 0-7，SMT 兄弟 16-23 空置；发布端、viewer、runner、签名桩和采集工具使用 8-15、24-31；隔离 netns `msperf-20261013T011210Z-7788320`；未修改任何全局配置。环境记录器每 10 s 记录一次频率、温度与负载（`raw/envlog-a2.tsv`）。
- 所有运行包由同一脚本 `tools/pr2.sh` 以相同参数启动：`--perf-stat --control-probe-ms 200 --input rtmp --sources 1 --warmup 15 --ready-timeout 240 --ramp-per-second 200 --group-size 256`；GB TCP 1 万路以上另加 `--gb-port-base 18700 --ready-timeout 300`，让监听端口避开服务端口与临时端口。
- **正式 A/B**（A = `rt-a2A-c999003`，B = B3 20 ms `rt-a2B3s20-c999003`，轮次名 `ab4-*`，任务 `094-ab4-formal-s20`，生成脚本 `tools/mkjobs_b4.sh`；GB TCP active 13000 与 13750 的加测为任务 `096-ab4-gbtcp-deep`，脚本 `tools/job096.sh`）：
  - 控制面：WHEP 3250/3500/3750 带 `--churn whep:50`，GB UDP 7500/8000 带 `--churn gb_udp:100`（每 20 s 一轮新会话或新 sender，持续 12 s 后断开），测量窗口 120 s；
  - 成本：GB TCP passive 7000、RTSP 6000、HTTP-FLV 6000、混合 7000（RTMP、FLV、RTSP、WHEP 各 1167，GB UDP、GB TCP passive 各 1166），窗口 60 s；
  - 容量与过载：GB TCP active 12000/13000、GB TCP passive 12000、RTMP 8500、RTSP 7750、混合 7250、RTMP 9000，窗口 60 s；
  - 交替顺序：每个负载点按 ABBA、BAAB、ABBAAB 或 BAABBA 运行；环境哨兵 RTMP 6500 在任务开头、中间和结尾各两对。
- 第二轮（A 对 B3 5 ms，`ab3-*`、`sel-*`）与第一轮（A 对 B2，`ab-*`、`cost-*`）用同样的参数与交替方法，数据在附录 A、B。三轮共用的 A 是同一个 ELF；三轮的哨兵（RTMP 6500）在 10 月 24 日和 26 日一致（6.5 节）。
- 采样分离：perf record、bpftrace、syscount 只用于诊断和剖析轮次（`raw/diag/`、`raw/prof/`）。A/B 轮次只有 `perf stat` 计数，以及每 200 ms 一次的控制探测（各版本相同）。
- 控制面指标：
  - **控制探测**：测量窗口内每 200 ms 发一次 `GET /receivers`（带控制 token，每次新建 TCP 连接），记录完成时间。请求串行，前一个未完成时不发下一个，因此超时多时请求数会减少。
  - **GB sender create/delete**：`gb_fanout` 记录每次 `/gb28181/sender/create`（爬坡与 churn）和窗口后 `/gb28181/sender/delete` 的耗时，客户端请求时限 10 s。
  - **WHEP 建立**：`whep_fanout` 记录每个会话从 POST 到 201、到 ICE+DTLS 完成的耗时，以及建立失败数；爬坡（main）与稳态 churn 分开统计。表中 p99 和最长取各客户端组的最大值。
- 媒体面指标：每个 viewer 的实时比例（视频媒体时间/墙钟）≥0.98、全部 viewer 都在前进、lag span（每个 viewer 窗口内墙钟与媒体时间之差的变化幅度）、RTP 序号与时间戳健康、UDP 丢包、TCP 重传。
- CPU 指标：服务端核数（`/proc/stat` 中 0-7 的繁忙核数）、`perf stat` 的 cycles/instructions（每 viewer 每秒）、IPC、上下文切换。

## 10 是否保留 A2

**保留 B3 20 ms。** 理由：

1. 修改直接对应已确认的根因。F4 在 WHEP 和 GB UDP 上是可重复的失败（A 在两个负载点都是 3 轮通过 1 轮），B 都是 3/3 通过，两个协议的稳定容量各提高一档。在两版都通过的负载点，控制面 p99 也降为原来的 1/5 左右。
2. 媒体吞吐、每 viewer 成本、媒体速率和丢包都没有变化。WHEP 的媒体延迟明显下降。
3. 代价 R1、R2 只出现在 GB TCP 的 CPU 拐点之后。上一轮报告已按延迟拐点把 GB TCP 的有效容量定在 9500～10000，12000、13000 属于过载区。即使在这一区域，12000 的通过率不变；13000 的边界轮次中，B 多 1/6 轮失败。
4. 实现只有一个编译期常量和每帧一次时间比较，没有新状态、锁、配置、线程或抽象，生命周期和顺序不变量与原实现相同。

如果以“GB TCP 过载区的爬坡 create 不得变慢”为硬性条件，就应回退。在本轮测过的时间片中，没有一个能同时满足 F4 与这一条件：5 ms 更差，B2 增加中等负载成本。

## 11 对 A1、A3 的下一步建议

- **A1（`tcp_transport` 持有待发缓冲）应作为下一步，并在 A2 之上验证。** 本轮证实，过载时 TCP 输出的成本依赖“drain 连续交付多少帧”：B2 让 GB TCP 中等负载的成本增加 16%，5 ms 让 GB TCP 12000 失败，20 ms 让过载区的爬坡 create 变慢（R1）。目前 GB TCP 的合并取决于 flush 在事件循环中的执行顺序（`output_` 为空时才 post flush），RTMP/RTSP/FLV 则逐次 post 并逐次 `async_write`。A1 改成“有写在途时只追加，写完成后一次写出全部积压”，合并只由 socket 的写完成节奏决定，不再依赖 drain 的长短。GB TCP sender 也应采用同样的方式。预期 A1 能同时消除 R1 和 F5 的积压来源。验收时重点测：GB TCP active 12000/13000 的爬坡 create 是否回到 A 的水平，RTMP 8750～9000 的 F5 是否消失，中等负载 RTMP/RTSP/FLV 成本是否下降。
- **A3（UDP 输入 `SO_RCVBUF`）与 A2 独立，可以单独实施。** A2 只改变输出分发；A3 针对的是 CPU 远未饱和时 UDP 输入 socket 因关键帧突发丢包（F6），本轮的输入都是 RTMP，没有涉及。A3 的 A/B 应使用 GB UDP 300 路、WHIP 150～200 路输入，以及 H.265 夹具经 GB UDP 输入，观察 `UdpRcvbufErrors` 和输入容量。
- 剩余的单帧交付尾部（约 200～360 ms）只在单组上千个同步 UDP sink 时出现，现在不建议继续拆分单帧交付。等 A1 完成后，如果控制面仍是瓶颈，再根据数据评估。
