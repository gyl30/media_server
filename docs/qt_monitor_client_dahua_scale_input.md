# 大华录像 Scale 的生产 HTTP 输入节奏取证

## 1. 范围与结论

2026-10-18，基于 `b24f4ab0f1ed7018574f092e0b1094b35415724c`，在同一真实大华录像 dialog 内调用既有生产 `/scale` 控制，持续读取生产 PS HTTP 正文；采集端不做在线解码或播放限速。两轮分别观察 `2→1→0.25→1` 和 `4→1→0.5→1`。实际双轨到达节奏随控制变化，但请求4倍的本轮窗口只有约3.43倍，不能以HTTP 204或请求值宣称实际4倍。

这是输入路径取证，不是 Qt Scale 呈现通过，也不是录像库存完整性验收；本轮未播放声音或执行物理听音。未修改生产源码、Qt 播放器、相机配置、平台地址、编码或音量。没有重复执行容量测试或全量构建；本次未重新运行 CTest、Go 或 Sanitizer。上一阶段 Qt seek 的限定 Normal/ASan 实机结果仍只属于[其原始验证范围](qt_monitor_client_dahua_qt_seek.md)。

## 3. 测量定义

用 DEV 实际 `/home/gyl/bin/ffprobe` 的 packet PTS/DTS 和 `pos`，映射到包含该 packet header 字节的 HTTP 正文读取区间，取该区间的 read-end 单调时间。**这是 packet header 的应用层可见到达时间，不是完整 AU 就绪时间、相机发送时间或精确切换边界。** 操作系统、TCP和HTTP缓冲仍可能造成偏差。

预先采用相同排除规则：初始窗口为首正文后2秒到第一次控制发起前1秒；后续窗口为当前响应完成后2秒到下一次控制发起前1秒，最后窗口止于最后正文前0.5秒。保护窗只用于避开过渡，不能声称响应后2秒即设备生效。回归为窗口内 PTS 对应用层墙钟的普通最小二乘斜率，单位为“媒体秒/墙钟秒”，不是重复多轮的置信区间；同时保存每0.5秒前进的2秒滑动窗。

PCMA 8bit/mono 的 packet 字节数等于样本数，除以完整窗口墙钟时长得到样本/秒。它受窗口两端分包影响，不等于逐样本精确发送速率。两轮分别2665、2301个 ffprobe 包全部映射成功，无未映射包。写盘 p95 分别0.025275、0.023522毫秒，最大7.973087、1.096583毫秒；未见足以解释倍率差异的写盘停顿，但这不能证明完全无缓冲。

独立只读复算确认以上映射、窗口与斜率。该相机本轮0.25倍确实改变双轨节奏，不能写成“设备忽略0.25”。视频/音频 PTS 非递减且本样本 PTS=DTS，但音频有重复 PTS 及两处120毫秒增量，视频最大70毫秒增量，不能据整体斜率称时间戳完全无抖动。

**原始采集整体仍为 `FAIL / TimeoutError`，不改写为 PASS。** 创建201、PS200、四次控制204、DELETE204，采集77.934480秒、保存33777070字节；最后正文在首正文后61.572974秒，约15.018秒无正文后采集器超时。独立 TCP 重组和 dechunk 得到完全相同字节及SHA，28768个完整 data chunk 后没有HTTP零终止chunk。MediaStatus121和BYE/200之后，采集器先FIN，不能称自然HTTP EOF或完整库存成功。

当前 `signaling/gb_playback.go:21` 的 `playbackDrainTimeout=20秒`，`finishPlayback()` 先发BYE、保留有界收尾，再清理 receiver。因此本轮采集器15秒无数据期限短于平台原20秒窗口，超时本身不足以证明生产缺陷。没有为获得PASS延长本轮数据、重写结果或绕过HTTP完整性要求；也没有声称已在更长读取期限下验证自然终止。

## 6. SIP、媒体身份、解码及SCR

- 两轮各只有一次INVITE/ACK、一个PS GET/HTTP200，INFO和BYE保持原dialog/双tag。第一轮4个逻辑INFO各重传一次，线上8个请求；第二轮4个逻辑INFO共5个请求，仅4倍事务重传一次。不把UDP重传算作新业务请求。
- 两轮各四次控制都有外层SIP200及匹配CSeq的内层MANSRTSP200；请求不携Range，响应无RTP-Info。设备响应没有证明实际Scale；媒体量与实际到达时间单独测量。第二轮BYE/200完整，DELETE204来自原采集记录。
- 两份原PS在DEV离线FFmpeg双轨解码均退出0，分别1599帧/63.929秒及1381帧/55.209秒。保留 null muxer 的重复DTS诊断，不称时间戳完全正常；第二轮主动截断也不能由退出0推导库存完整性。
- 离线命令使用 `ffmpeg -nostdin -hide_banner -threads 1 -i media.ps -map 0:v:0 -map 0:a:0 -progress decode-progress.txt -f null -`。CLI实际7.1.1，与 Qt 当前 FFmpeg9.0.1 shared SDK不同；没有把 CLI 退出0当作 Qt 实际呈现、PCM精确对照或当前SDK ASan验证。
- SCR解析按项目锁定 `third/ireader/libmpeg/source/mpeg-pack-header.c` 的 `pack_header_read()` 位布局，未修改依赖。两轮1599/1381个pack的SCR墙钟斜率与视频PTS几乎相同：2倍约1.947、0.25倍约0.2505、4倍约3.433、0.5倍约0.4997。SCR不是本样本的独立1倍墙钟，不能仅用PTS/SCR推导实际倍率。

## 9. 对下一步Qt实现的约束

现有 `decode_thread` 固定8k→48k重采样、有限视频/PCM队列与 SDL 48k消费在背压下会把快输入重新限为普通播放。不得直接用requested倍率当实际倍率，也不能靠丢音、静音或仅增长解码计数宣称完成。

只读复审确认：解码/有界预取发生背压后，读取时间已受本地消费影响，不能继续把它称为可靠设备到达速率。可以研究只在Scale操作后启用的有界队列反馈自适应，但必须明确是best-effort呈现，保留普通未Scale有限回放原行为；音频实际变速后还需要按各段源媒体跨度与输出样本数映射SDL时钟，不能继续以整队列字节数除以192000作为媒体时间。

另外，当前10毫秒计时器每次仅提交一帧，4倍×25fps已达100fps理论上限。连续覆盖image并合并paint不能当成每帧真实显示；硬件刷新率不足时，不可能同时承诺严格4倍与全部独立图像物理显示。应记录呈现能力和有意选择的策略，不为通过验收伪造计数。

下一步先用定时真实双轨PS夹具建立固定1倍播放的RED，覆盖实际加速、减速、请求被忽略、网络突发/GUI停顿、seek与EOF；再按最小可维护方案实现并验证实际可听音频、媒体时钟、图像和资源回收。本页不宣称该生产实现或真实Qt Scale测试已经完成，整个阶段四、阶段六和平台仍未GO。
